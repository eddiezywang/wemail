# 邮箱密码恢复后的断档补偿同步设计

## 背景与根因

密码更新功能已经能够恢复 IMAP 登录，但运行态验收发现恢复后只显示“更新 1 封”，密码失效期间的新邮件没有全部补齐。

现场数据表明，INBOX 本地游标为 `1673549105`，而服务器当前最新邮件 UID 为 `1667488176`。目标企业邮箱 IMAP 在 `UIDVALIDITY` 仍为 `1` 的情况下发生了 UID 回退。现有增量同步假设 UID 永远递增，使用 `<cursor + 1>:*` 查询时只得到服务器末尾一封已有邮件，因此每轮都表现为 `inserted=0 updated=1`。

## 目标

- 密码恢复后补齐最近 30 天内因凭据失效而遗漏的全部邮件。
- 自动识别 UID 回退，让后续增量同步不再长期漏信。
- 修复失效的本地游标，使补偿完成后的增量同步重新正常工作。
- 用户只执行“更新密码”，同步恢复作为后台行为，不在按钮或进度文案中出现“重试”。

## 方案比较

### 采用方案：恢复时窗口同步，并对 UID 回退自动降级

密码更新成功后执行最近 30 天的时间窗口同步。增量查询若返回任何小于或等于当前游标的 UID，则判定服务端 UID 已回退，返回“游标失效”，沿用现有逻辑自动降级到时间窗口同步。

优点是既能立即补齐当前断档，也能修复以后同类 UID 回退；实现复用现有 `syncWindow` 和增量 fallback 结构，不需要数据库迁移。

### 未采用方案一：只把密码恢复后的同步改为 30 天窗口

能解决当前恢复流程，但日常增量同步仍可能在下一次 UID 回退后永久漏信。

### 未采用方案二：新增“最后成功同步时间”数据模型

语义更完整，但需要数据库迁移、每文件夹时间状态和更多恢复规则。当前已有时间窗口 fallback 足以解决问题，不增加新的持久化状态。

## 后端同步设计

### UID 回退检测

`ImapSmtpMailProvider.syncAfterCursor()` 执行 UID 范围查询后：

- 正常情况下，所有返回 UID 都必须大于本地 `cursor.uid`；
- 如果存在 `uid <= cursor.uid`，记录不含邮件内容的安全日志；
- 返回 `null` 表示游标不可继续使用。

`Mail Core sync worker.syncIncremental()` 已把 `null` 解释为游标失效，并自动执行指定天数的 `syncSince()`，因此无需新增异常或 API 错误。

### 游标修复

时间窗口同步会抓取窗口内各文件夹邮件，并按本次返回结果重新保存每个文件夹的最大 UID。由于最近 30 天结果属于服务器当前 UID 空间，旧的异常高游标会被当前有效 UID 替换。

### 密码恢复补偿窗口

密码更新验证成功后，客户端调用：

```json
{
  "mode": "window",
  "days": 30
}
```

该同步进入现有 `Mail Core sync worker` 串行队列，与账号重建后自动启动的 background watcher 不会并发写库。

## 客户端文案与交互

- 主按钮从 `更新并重试` 改为 `更新密码`。
- 提交中保持 `正在验证…`，表达密码验证而非同步重试。
- 说明文案保留“更新后自动恢复同步”，明确同步是系统行为。
- 组件、测试名称中的技术性 retry 可以保留，但所有用户可见文案不得出现“重试”。
- 密码保存成功后，在后台等待 30 天补偿同步完成；成功仍提示 `密码已更新，邮件同步已恢复`。
- 补偿同步因普通网络问题失败时，提示密码已更新但同步暂时失败，不再次要求输入密码。

## 测试

- provider 收到全部大于游标的 UID 时继续增量抓取。
- provider 收到小于或等于游标的 UID 时返回 `null`，且不抓取错误范围。
- sync service 收到 `null` 后执行 30 天窗口 fallback 并保存新游标。
- 密码弹窗提交成功后调用 `mode: window, days: 30`。
- 按钮和提交阶段的用户可见文案不包含“重试”。
- 完整服务端测试、渲染测试、类型检查和桌面构建通过。

## 元数据优先同步优化

对 `mail.example.com` 的运行态探测确认，批量 FETCH 本身可用：一次抓取
500 封邮件元数据约 3 秒，没有触发 volume limit。真正耗时的是完整 RFC822
正文：100 封邮件约传输 176 MB，耗时约 62 秒。

因此补偿同步和常规增量同步仍遍历所有可同步文件夹，但每批最多 500 封，
只抓取 UID、信封、正文结构和服务器内部时间。完整邮件源在用户打开邮件时
按单封下载；下载完成后再启动该邮件的智能处理。

元数据更新不得覆盖本地已经缓存的正文。未下载正文的邮件不进入自动智能处理；
按需下载并落库后，再为该邮件触发智能处理，避免处理器把“正文尚未下载”误判为
“正文为空”。

## 验收标准

1. 密码更新后，最近 30 天的缺失邮件全部进入本地邮件库。
2. 当前异常高 INBOX 游标被服务器当前 UID 空间中的有效游标替换。
3. 后续 idle/polling 增量同步不再反复出现 `inserted=0 updated=1` 的假同步。
4. 弹窗主按钮显示“更新密码”，用户界面不出现“重试”。
