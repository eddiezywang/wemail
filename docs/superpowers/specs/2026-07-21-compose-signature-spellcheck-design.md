# WeMail 邮件签名排版与拼写白名单设计

## 背景

当前自动签名由 `app/lib/utils.ts` 的 `getSignatureBlock` 生成，并通过 `data-wemail-signature="true"` 插入富文本编辑器。签名已经位于用户正文之后、原邮件引用之前，但签名内容与 `Sent with WeMail` 之间使用了 24px 间距，视觉上像两个无关区块。

正文编辑器使用 Chromium/Electron 的原生拼写检查。产品名 `WeMail` 和当前账号用户名会被当作未知英文词标红，而正文中的 `AIMC` 等非白名单词应继续接受系统拼写检查。

## 目标

- 自动签名保持在邮件正文的同一文本流中，左对齐并紧跟正文。
- 回复和回复全部场景继续使用“正文 → 签名 → 原邮件引用”的顺序。
- 缩短签名内容与品牌尾注之间的距离，降低品牌尾注的视觉权重。
- 在整个邮件正文富文本编辑器内，免除 `WeMail` 和当前账号身份词的红色拼写波浪线。
- 不豁免 `AIMC` 或任意自定义签名文本中的其他未知词。
- 不修改操作系统词典，也不向发出的邮件 HTML 写入拼写检查专用标记。

## 非目标

- 不关闭编辑器的整体拼写检查。
- 不实现用户可编辑的个人词典或设置界面。
- 不改变拼写检查语言、词典下载地址或系统建议菜单。
- 不修改签名启用状态、自定义签名存储结构或账号切换逻辑。
- 不改变邮件发送协议、服务端正文处理或引用原文格式。
- 不将主题、收件人、抄送和密送输入框纳入本次白名单；范围仅为正文富文本编辑器。

## 方案选择

采用 TipTap/ProseMirror 的编辑器内联装饰实现应用级拼写白名单。

未采用 Electron `session.addWordToSpellCheckerDictionary`，因为该 API 在 Windows 和 macOS 会写入操作系统自定义词典，造成超出 WeMail 的持久副作用，也无法覆盖纯浏览器运行方式。未采用将 `spellcheck="false"` 标签持久写入正文 HTML，因为这会把仅供编辑器使用的行为泄漏到草稿和最终邮件，并增加复制、粘贴和正文清理的复杂度。未采用关闭整个签名块的拼写检查，因为这会同时隐藏自定义签名里的 `AIMC` 等真实未知词。

## 签名位置与视觉排版

### 文本流位置

签名继续作为正文文档中的普通块级节点存在：

```text
用户编写的邮件正文
自动或自定义签名
原邮件引用（仅回复类邮件）
```

- 签名不进入右侧面板、独立列、浮动层或固定底栏。
- 签名、正文和引用原文全部左对齐。
- 新建邮件没有引用原文，因此签名是正文文档的最后一个内容块。
- 回复、回复全部和转发沿用现有插入流程；本次只调整签名内部样式，不重排引用逻辑。
- 保留 `data-wemail-signature="true"`，使 AI 草稿逻辑和正文空态判断继续识别受保护签名区域。

### 视觉样式

生成的签名使用邮件客户端兼容的内联样式：

- 签名块与用户正文之间保留约 18px 的上间距。
- 签名内容使用正常的左对齐文本流；纯文本默认采用约 13px 字号和紧凑行高，自定义 HTML 保留经过清理后的内部格式。
- `Sent with WeMail` 位于签名内容的下一行，间距约 5px，不与用户名横向并排。
- 品牌尾注使用约 11px 字号和弱化中性色；仅 `WeMail` 使用现有 coral 品牌色及适度字重。
- 不增加卡片、背景块、右对齐、图标或分隔线，避免自动签名抢占正文注意力。

签名关闭、既有草稿保留、用户手动删除签名以及 AI 不改写签名等现有行为保持不变。

## 拼写白名单

### 白名单来源

每个草稿窗口按当前账号生成白名单：

1. 固定产品名 `WeMail`；
2. 当前账号 `displayName` 中的非空文字词；
3. 当前账号 `emailAddress` 的 `@` 前用户名；
4. 邮箱前用户名中由常见分隔符拆出的非空片段，用于覆盖浏览器将 `john.smith` 分别检查为 `john` 和 `smith` 的情况。

白名单不读取 `customText`。因此用户在自定义签名中写入 `AIMC` 不会让它自动成为合法词。账号尚未加载或邮箱格式异常时，只启用固定产品词 `WeMail`，编辑器仍可正常使用。

白名单在进入编辑器前执行以下归一化：

- 去除首尾空白；
- 丢弃空字符串；
- 按不区分大小写的形式去重；
- 保留原始展示字符，仅将小写形式用于匹配；
- 不把一个白名单词的子串视作命中。

### 匹配规则

- 匹配覆盖正文编辑器内的全部文本节点，包括用户输入、粘贴内容、自动签名和引用原文。
- 英文匹配不区分大小写，因此 `WeMail`、`wemail` 和 `WEMAIL` 均可命中。
- 只匹配完整候选词；例如豁免 `WeMail` 不会豁免 `WeMailer`。
- `AIMC` 未出现在账号身份或固定白名单中时，不生成豁免装饰，继续由原生拼写检查显示红色波浪线。
- 文档更新、粘贴和账号身份更新后重新计算装饰，避免只覆盖首次渲染内容。

### 编辑器装饰

新增一个聚焦职责的 TipTap 扩展，例如 `SpellcheckExemptions`。扩展维护当前白名单，并为命中的文本范围创建 ProseMirror inline decoration：

```html
<span
  data-wemail-spellcheck-exempt="true"
  spellcheck="false"
>WeMail</span>
```

这些 `span` 仅存在于编辑器 DOM：

- `editor.getHTML()` 不包含装饰节点；
- 保存草稿和发送邮件的 HTML 不增加白名单属性；
- 用户复制或编辑正文时，文档模型仍只包含原始文本；
- 原生拼写检查继续处理没有装饰的文本。

扩展通过带元数据的 ProseMirror transaction 接收白名单更新，避免为了账号数据变化销毁并重建编辑器。插件状态同时保存归一化白名单和当前 `DecorationSet`；文档变化或白名单变化时重新构建装饰，否则复用现有结果。

## 组件与数据流

1. `useComposeForm` 从当前账号和邮箱数据构建签名内容，同时生成正文编辑器所需的拼写白名单。
2. `ComposeBody` 和仍在使用的 `ComposeEmail` 将白名单传给 `RichTextEditor`，保证两种草稿入口行为一致。
3. `RichTextEditor` 将白名单同步给 `SpellcheckExemptions` 扩展。
4. 扩展扫描当前 ProseMirror 文档并创建非持久化 inline decorations。
5. 用户输入或粘贴内容时，文档 transaction 触发装饰重算；`onChange` 仍返回不含装饰的正常邮件 HTML。
6. `getSignatureBlock` 只负责新的单列签名样式和现有安全清理，不承担拼写白名单逻辑。

职责保持分离：账号身份决定“允许哪些词”，编辑器扩展决定“如何在界面中豁免”，签名生成器决定“邮件里实际发送什么”。

## 错误与边界处理

- 当前账号缺失时仅豁免 `WeMail`，不阻塞正文初始化。
- `displayName`、邮箱用户名或片段为空时直接忽略。
- 重复词和大小写变体只生成一组装饰。
- 特殊字符在匹配前按普通文本处理，不直接拼接未经转义的正则表达式。
- 一个文本节点内出现多次白名单词时，每个完整命中范围都生成装饰。
- 富文本格式将一个视觉词拆为多个文本节点时，不跨节点合并匹配；这是可接受的保守行为，避免破坏 ProseMirror mark 边界。
- 装饰计算失败或收到空白名单时返回空 `DecorationSet`，编辑器退化为系统原生拼写检查。

## 测试与验收标准

### 自动化测试

- 纯函数测试白名单归一化、大小写去重、显示名拆词、邮箱前用户名和常见分隔符片段。
- 纯函数测试完整词匹配、多次匹配和子串不匹配。
- `RichTextEditor` 组件测试确认正文任意位置的 `WeMail` 和当前账号用户名拥有 `spellcheck="false"` 装饰。
- 组件测试确认 `AIMC` 没有豁免属性，即使它出现在自定义签名或普通正文中。
- 组件测试确认编辑、粘贴和白名单 prop 更新后装饰同步更新。
- 组件测试确认 `onChange` 与 `editor.getHTML()` 不包含 `data-wemail-spellcheck-exempt`。
- `getSignatureBlock` 测试确认品牌尾注位于签名内容下方、间距收紧、左对齐且继续保留 `data-wemail-signature`。
- `useComposeForm` 测试确认回复正文顺序仍是正文、签名、引用原文，既有草稿不被重写。

### 人工桌面验收

- 在 Windows Electron 草稿窗口中，正文和自动签名里的 `WeMail` 不显示红色波浪线。
- 当前账号用户名无论位于正文还是签名中均不显示红色波浪线。
- 同一封邮件中的 `AIMC` 仍显示红色波浪线。
- 输入 `WeMailer` 时仍由系统词典检查，不因 `WeMail` 白名单发生子串豁免。
- 新建邮件签名位于正文最下方；回复邮件签名位于正文与原邮件引用之间，且全部左对齐。
- 签名内容与品牌尾注间距紧凑，品牌尾注不抢正文视觉层级。
- 保存草稿后重新打开，正文 HTML 中不存在 `data-wemail-spellcheck-exempt`。

## 完成定义

相关纯函数、编辑器、签名和草稿初始化测试通过，项目类型检查通过，并在 Windows Electron 中完成上述人工验收后，才视为实现完成。
