# Agent 首页初始化与情境化推荐提示词设计

## 背景

WeMail AI 首页当前存在两个相互关联的问题：

1. 当 `agentSessionId` 为空时，客户端仍回退到固定的 `mailboxId` 作为会话 ID，并自动读取该会话的历史消息。因此用户回到邮箱首页时看到的可能是最近一次邮箱级对话，而不是稳定的初始化状态。
2. 首页推荐提示词虽然已经能够读取部分账户摘要状态，但仍偏向固定功能入口或系统任务，例如“查看未读”“待办”“重试失败摘要”。它们没有充分反映用户当天真实收到的邮件，因此缺少“AI 已经读过我的邮箱并知道我现在该做什么”的体验。

本设计将邮箱首页与历史会话恢复分离，并将推荐提示词升级为由当天真实邮件驱动的可执行意图。

## 目标

- 用户进入没有选中邮件的邮箱首页时，始终看到新的初始化会话。
- 历史会话只有在用户主动选择后才恢复。
- 推荐提示词基于用户当地日期内收到的真实邮件生成。
- 未读、明确要求行动、未完成待办和临近截止时间的邮件获得更高优先级。
- 首页不等待模型调用即可展示可用建议。
- AI 聚合只处理少量高分候选，并通过缓存、去重和静默更新控制延迟与调用量。
- 推荐提示词保持轻量，不把首页变成任务中心。

## 非目标

- 本次不改变选中具体邮件后的邮件级会话恢复行为。
- 本次不建设通用任务中心或新的摘要中心页面。
- 本次不展示评分明细、推荐证据卡或关联邮件列表。
- 本次不使用完整邮件正文作为首页聚合输入。
- 本次不引入用户可编辑的权重设置。

## 体验设计

### 首页初始化状态

当用户位于邮箱首页且没有选中具体邮件时：

- Agent 面板不使用 `mailboxId` 查询或恢复历史对话。
- 页面显示初始化欢迎语、当天邮件概况和最多三条推荐提示词。
- 新的会话 ID 延迟到用户首次发送消息或点击推荐提示词时创建。
- 点击清空当前对话后回到相同的初始化状态。
- 用户从历史会话列表主动选择会话后，才设置显式会话 ID 并加载对应消息。

初始化状态与“没有消息的已存在历史会话”必须在状态模型中保持可区分，避免后续再次通过固定邮箱 ID 隐式恢复历史。

### 推荐提示词外观

采用轻量提示词方案：

- 保留 `Hi 用户名` 欢迎语。
- 副标题使用真实的当天概况，例如“今天有 18 封新邮件，其中 6 封建议优先处理”。
- 下方显示最多三条圆角提示词按钮。
- 不增加“邮件行动建议”等区块标题。
- 不在按钮中展示评分、邮件数量或推荐原因。
- 不展示后台 AI 的加载状态、完成提示或 Toast。

提示词应表达可执行意图，而不是产品功能名称。例如：

- 处理今天尚未回复的 服务台 与 DocFlow 待办
- 汇总需要确认或提交材料的项目邮件
- 整理今天收到的会议和会员动态通知

点击提示词后，应把提示词对应的关联邮件范围传给 Agent，而不是只发送一段需要再次模糊搜索的自然语言。

### 静默更新保护

规则结果可以在 AI 聚合完成后被静默替换，但必须满足以下条件：

- 用户尚未点击任一推荐提示词。
- 用户尚未在输入框中输入内容。
- 当前初始化会话尚未产生任何消息。
- 用户没有切换邮箱、选中邮件或恢复历史会话。

任一条件不满足时，本轮推荐列表立即冻结。静默替换使用短暂淡入，不移动输入框，也不显示通知。

## 当天邮件范围

“当天”按账户当前运行环境的用户本地时区计算自然日边界。服务端查询使用明确的起止时间，避免直接依赖数据库 UTC 日期截断。

首版只考虑当天收到的邮件。若当天没有合格候选，则退回通用的账户级建议，不自动扩大到最近七天。扩大时间范围可在后续版本中单独设计。

## 确定性评分

评分在服务端使用结构化数据完成。初始权重如下：

| 信号 | 分值 |
| --- | ---: |
| 未读 | +40 |
| 明确要求回复、确认或提交材料 | +35 |
| 存在未完成的邮件待办 | +30 |
| 截止时间在 24 小时内 | +25 |
| 截止时间在 3 天内 | +15 |
| 重要联系人 | +10 |
| 重复催办或同主题再次到达 | +10 |
| 当天新近程度 | 0 至 +10 |
| 已回复 | -35 |
| 关联待办已完成 | -40 |
| 营销或订阅邮件 | -25 |
| 普通系统通知 | -15 |

评分信号可以叠加。权重集中在单一配置模块中，并为每个得分项保留机器可读的 reason，便于测试、调试和后续离线评估。

明确行动请求优先使用现有邮件智能结果，包括回复判断、摘要行动项、待办提取和截止时间；缺少智能结果时才使用保守的结构化或文本规则。不能因为摘要任务失败而阻塞推荐生成。

## 规则提示词生成

确定性阶段必须能够独立返回可用结果，以保证首页首屏不依赖模型。

流程如下：

1. 查询当天邮件及其已有智能结果和处理状态。
2. 计算评分并过滤非正向候选。
3. 按得分、截止时间和接收时间排序。
4. 选取最高分候选。
5. 通过行动类型、主题关键词、发件人或线程关系做简单聚合。
6. 生成最多三条规则提示词及其关联邮件 ID。

规则提示词可以比 AI 结果更概括，但必须是可点击执行的完整意图，不能返回空白骨架。

## AI 聚合

AI 只接收评分最高的最多 12 封候选邮件。每封候选仅包含：

- 邮件 ID
- 主题
- 发件人显示名及必要的域信息
- 已有摘要
- 已提取的行动项和截止时间
- 未读、已回复和待办完成状态
- 确定性评分及评分原因

不发送完整正文或无关附件内容。

模型输出为最多三项的严格结构化结果，每项包含：

- 稳定的建议 ID
- 用户可见的简短标签
- 发给 Agent 的完整执行指令
- 关联邮件 ID 列表
- 聚合类别

服务端验证所有关联邮件 ID 必须来自输入候选集合，去除空标签、重复标签和没有关联邮件的结果。验证失败时保留规则结果。

## 性能与缓存

### 两阶段返回

建议接口应支持以下状态：

- `rules`：立即可用的规则结果。
- `cached-ai`：候选指纹匹配的已缓存 AI 结果。
- `refreshing`：服务端已经返回规则或缓存结果，同时在后台生成新结果。

客户端首个响应只渲染当前可用结果，不等待后台 AI。

### 候选指纹

缓存键至少包含：

- 账户 ID
- 用户当地日期
- 排序后候选邮件 ID
- 候选邮件的处理状态和相关智能结果版本
- 推荐提示词版本

只有候选指纹变化时才需要重新聚合。单纯重复打开 Agent 面板不能产生新的模型调用。

### 增量失效

以下事件可能使缓存失效：

- 同步到新的当天邮件
- 邮件被读或标记未读
- 邮件被回复
- 关联待办创建、完成、恢复或删除
- 摘要、回复判断、行动项或截止时间结果发生变化
- 重要联系人状态变化

短时间内的连续变化合并处理，建议防抖窗口为 10 至 30 秒。同一账户同一候选指纹只允许一个在途 AI 聚合任务。

### 超时与失败

- AI 聚合是后台增强，不得阻塞规则结果。
- 模型超时、配置缺失、输出验证失败或服务异常时，继续使用规则结果。
- 失败不在首页展示错误。
- 后台失败应记录可观察的错误码和耗时，但不得记录邮件正文或敏感内容。

## 客户端状态模型

客户端需要显式区分：

- `home-initial`：邮箱首页初始化状态，没有会话 ID。
- `home-active`：从首页首次交互后创建的新会话。
- `email-context`：选中具体邮件的现有行为。
- `history`：用户主动恢复的历史会话。

推荐提示词只在 `home-initial` 且消息数为零时展示。恢复历史会话时不展示首页推荐。

建议响应更新时，客户端比较当前交互锁与候选指纹。只有仍处于未交互的 `home-initial` 状态时才静默替换。

## 接口与数据契约

现有 `GET /api/agent/suggestions` 可以演进为返回：

```ts
interface AgentSuggestionResponse {
  suggestions: Array<{
    id: string;
    label: string;
    prompt: string;
    emailIds: string[];
    action?: AgentSuggestionAction;
  }>;
  contextLine?: string;
  source: "rules" | "cached-ai";
  candidateFingerprint: string;
  refreshPending: boolean;
}
```

后台聚合结果可以通过现有查询失效机制、轻量轮询或邮件事件通道通知客户端。实现计划应优先复用项目已有事件能力，避免为单一功能引入新的实时连接。

## 隔离与模块边界

建议拆分为以下职责：

- 当天候选查询：只负责获取账户范围内当天邮件及结构化状态。
- 评分器：纯函数，根据输入信号输出分数和 reasons。
- 规则聚合器：纯函数，把排序候选变成即时提示词。
- AI 聚合器：负责有限输入、结构化输出和验证。
- 缓存与刷新协调器：负责指纹、去重、防抖和后台刷新。
- 首页会话状态：客户端负责初始化、显式历史恢复和交互冻结。

评分和规则聚合应保持纯函数，以便在不启动运行时或模型的情况下进行完整单元测试。

## 测试策略

### 服务端单元测试

- 未读邮件获得高于普通已读通知的分数。
- 明确行动请求、未完成待办和临近截止时间正确叠加。
- 已回复、已完成、营销和普通通知正确降权。
- 当天边界按指定时区计算。
- 规则聚合最多返回三项，并保留正确邮件 ID。
- AI 输入最多包含 12 封邮件且不包含正文。
- AI 输出不能引用候选集合外的邮件 ID。
- 相同候选指纹复用缓存并去重在途任务。
- AI 失败、超时和非法输出回退到规则结果。

### API 测试

- 建议接口只返回当前账户数据。
- 响应包含来源、指纹和刷新状态。
- 没有模型配置时仍返回规则建议。
- 当天无候选时返回安全的通用账户建议。

### 客户端测试

- 邮箱首页不再使用 `mailboxId` 恢复历史消息。
- 首次发送或点击提示词时创建新会话。
- 主动选择历史会话仍能恢复消息。
- 清空对话回到初始化状态。
- 推荐只在空白首页会话显示。
- AI 结果仅在用户未交互时静默替换。
- 输入、点击、切换邮件或恢复历史后推荐冻结。
- 点击聚合建议时携带正确邮件 ID 范围。

### 性能验收

- 有本地数据时，规则建议不依赖外部模型响应即可返回。
- 重复打开面板且候选不变时不增加模型调用。
- 大量当天邮件仍只向 AI 发送最多 12 个候选。
- 多个连续邮件状态事件被合并为一次后台刷新。

## 发布与兼容

- 保留现有建议接口的核心字段，使现有客户端在过渡期仍能读取 `id`、`label`、`prompt` 和 `action`。
- 新字段采用向后兼容扩展。
- 若 AI 聚合能力未配置或被关闭，产品仍以规则建议完整工作。
- 首版权重和候选上限作为服务端常量发布，后续根据日志中的匿名化 reason 分布和点击率调整。

## 已确认决策

- 使用“规则评分 + AI 聚合”，不采用纯规则或纯 AI。
- 首版以当天收到的邮件为主要数据范围。
- 未读权重最高，其次考虑明确行动请求和未完成待办。
- 使用轻量推荐提示词，不使用证据卡或任务卡。
- AI 完成后静默替换，不显示处理中或完成提示。
- 用户开始交互后冻结当前建议。
- 邮箱首页优先进入初始化会话，历史会话只能主动恢复。
