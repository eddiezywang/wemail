# WeMail 元数据优先与后台正文增量同步设计

## 背景

运行态验证表明，`mail.example.com` 支持批量 IMAP FETCH，并未观察到邮件元数据抓取的 volume limit。一次抓取 500 封邮件元数据约耗时 3 秒；抓取 100 封完整 RFC822 正文约传输 176 MB，耗时约 62 秒。因此同步慢的主要原因是完整正文的数据量，而不是文件夹遍历或 FETCH 命令数量。

当前实现已将列表同步改为元数据优先，并在用户打开邮件时按需下载正文。本设计在此基础上增加可恢复的后台正文增量同步，使列表尽快可用，同时在后台逐步补齐本地正文和智能处理数据。

## 目标

1. 遍历所有可同步文件夹，优先完成邮件元数据同步并立即展示列表。
2. 元数据同步不等待完整正文下载。
3. 后台按最新邮件优先逐步补齐正文，应用重启后继续剩余任务。
4. 分别记录元数据同步和正文同步的最近成功时间。
5. 正文下载失败、断网或密码过期不能丢失任务，也不能阻塞整个正文队列。
6. 用户打开未缓存邮件时，正文下载获得最高优先级。
7. 正文落库后再触发依赖正文的智能处理，并保证幂等。

## 非目标

- 不在本阶段实现正文缓存淘汰策略。
- 不根据电池状态、计费网络或系统空闲状态动态调速。
- 不增加手动管理正文下载队列的 UI。
- 不改变附件按需下载策略。

## 方案选择

### 采用：邮件表作为持久化正文任务集

`mail_messages` 表中的正文缓存状态直接表示任务进度。未缓存正文的邮件就是待处理任务，后台 worker 按条件查询并下载。用户打开邮件时走相同的正文落库路径，成功后该邮件自然从待处理集合消失。

该方案不需要维护独立任务表与邮件表的一致性，应用退出或崩溃后也不需要重建任务队列。

### 未采用：独立正文任务队列表

独立队列表能表达更复杂的任务状态，但会增加任务创建、去重、邮件删除和账号切换时的一致性维护。当前需求可以由邮件缓存状态和少量重试字段完整表达。

### 未采用：每文件夹正文 UID 游标

正文 UID 游标适合严格顺序同步，但与“最新优先”冲突。跳过失败邮件、用户打开邮件插队和跨文件夹排序都会形成难以表达的游标空洞。

## 数据模型

### 账号级同步状态

新增 `mail_sync_state`，以 `account_id` 为主键，至少包含：

- `metadata_synced_at`：一次全文件夹元数据同步全部成功提交后的时间。
- `body_synced_at`：最近一次正文成功落库的时间。
- `updated_at`：状态行最后更新时间。

`metadata_synced_at` 和 `body_synced_at` 语义独立。正文同步较慢或失败，不得回退或清空元数据成功时间。

`body_synced_at` 表示后台正文最近有成功进展，不表示所有正文已经补齐。是否追平由实时统计的 `pendingBodyCount` 判断，只有 `pendingBodyCount = 0` 才表示当前本地正文已追平。

### 邮件级正文状态

沿用正文缓存字段判断正文是否已下载，并为失败恢复增加：

- `body_fetch_attempts`：连续失败次数，成功后归零。
- `body_fetch_next_retry_at`：该邮件下次允许尝试的时间。
- `body_fetch_last_error_code`：不包含凭据、正文或服务器原文的安全错误码。

未缓存正文且未处于退避期的邮件是可调度任务。邮件删除后任务随邮件行自然消失。

## 架构

### 元数据同步管线

现有元数据同步继续负责：

1. 遍历所有可同步文件夹。
2. 批量抓取 UID、信封、正文结构和 IMAP INTERNALDATE。
3. 幂等写入邮件行并保存每文件夹 UID/UIDVALIDITY 游标。
4. 所有文件夹结果成功提交后更新 `metadata_synced_at`。
5. 唤醒正文 worker。

列表 API 不等待正文 worker，元数据落库后立即可见。元数据更新必须保留已经缓存的正文和正文缓存状态。

### 正文同步管线

新增独立的 `MailBodySyncWorker`，使用独立 IMAP 会话，避免大正文 FETCH 占用元数据同步连接。

worker 单并发逐封下载完整 RFC822 源，每轮默认最多处理 10 封。每轮结束后让出执行权，再根据剩余任务决定继续或休眠。批次大小和轮次间隔作为内部可配置参数保留，不提供用户设置。

每封正文成功后：

1. 解析正文并更新邮件缓存字段。
2. 清除该邮件的失败次数、退避时间和错误码。
3. 更新账号的 `body_synced_at`。
4. 发出统一的 `mail-hydrated` 事件。

### 前台按需下载

用户打开未缓存邮件时，将该邮件加入正文 worker 的高优先级入口。前台请求等待该单封下载完成并返回正文。

前台下载与后台下载使用同一个单封任务去重机制。如果后台已在下载同一邮件，前台复用该 Promise；如果尚未开始，该邮件移动到队列最前面。正文落库仍走统一的持久化和 `mail-hydrated` 事件路径。

### 智能处理

元数据邮件不直接进入依赖正文的智能处理。`IntelligenceOrchestrator` 监听 `mail-hydrated`，在正文成功落库后幂等创建该邮件的智能任务。

后台正文补齐和用户打开邮件触发的正文下载必须产生相同事件语义。已有成功或正在执行的智能任务不得重复创建。

## 调度策略

### 最新优先与防饥饿

每轮最多 10 封：

- 最多 9 封按 `received_at DESC` 选择最新的可调度邮件。
- 如果仍有更老的待处理邮件，保留 1 个名额处理最老邮件。

用户主动打开的邮件优先级高于上述后台排序。该策略保证最近邮件和智能结果优先可用，同时避免持续收取新邮件时历史邮件永久饥饿。

### 唤醒条件

以下事件唤醒 worker：

- 应用为当前账号完成启动。
- 元数据同步提交新邮件或发现未缓存邮件。
- 用户打开未缓存邮件。
- 网络从不可用恢复。
- 密码更新验证成功并完成元数据恢复同步。
- 正文退避时间到期。

没有可调度任务时 worker 休眠，不进行固定空轮询。应用退出或账号切换时停止 worker 和专用 IMAP 会话，但不清除邮件级任务状态。

## 并发与一致性

- 元数据同步继续使用现有串行同步队列。
- 正文 worker 使用独立 IMAP provider/session，正文内部并发固定为 1。
- 单封正文下载按邮件 ID 去重，前台和后台不能同时 FETCH 同一封邮件。
- 正文写入和邮件级失败状态更新在同一数据库事务内完成。
- `metadata_synced_at` 只在一次元数据同步整体成功后更新，部分文件夹失败不得更新时间。
- `body_synced_at` 只在至少一封正文成功持久化后更新。

## 错误处理

### 单封邮件错误

解析错误、邮件不存在或单封 FETCH 错误只影响该邮件。记录安全错误码并使用指数退避，worker 继续处理本轮其他邮件。达到退避上限后仍保留任务，后续低频再次尝试，不进入永久失败状态。

### 网络错误

连接级错误终止当前轮次，关闭失效会话并按指数退避重新连接。已成功落库的邮件不回滚，未开始和失败邮件仍由数据库状态保留。

### 密码失效

正文 worker 识别现有凭据失效错误，暂停后台正文同步并触发现有密码更新弹窗。密码更新成功后：

1. 先执行元数据恢复同步。
2. 更新 `metadata_synced_at`。
3. 再唤醒正文 worker 继续剩余任务。

后台自动恢复行为不出现在面向用户的按钮文案中。

## API 与展示状态

提供账号级同步状态读取能力，返回：

- `metadataSyncedAt`
- `bodySyncedAt`
- `pendingBodyCount`
- `bodyWorkerState`：`idle | running | backoff | credential-required | stopped`
- 可选的安全 `lastBodyErrorCode`

列表页可以显示“邮件列表更新于…”和“正文同步中，剩余 N 封”。正文 worker 错误不应把已经成功的元数据列表标记为不可用。

## 测试策略

### Repository

- 元数据更新不覆盖已缓存正文。
- 未缓存正文查询支持最新优先和最老防饥饿名额。
- 正文成功清除失败状态并更新缓存。
- 失败次数、退避时间和安全错误码正确持久化。
- `pendingBodyCount` 与缓存状态一致。

### Worker

- 单并发、每轮最多 10 封。
- 默认最新优先，并处理一封最老任务。
- 前台打开邮件可以插队并复用同一下载 Promise。
- 单封失败不阻塞后续邮件。
- 网络错误停止当前轮并退避。
- 密码错误进入 `credential-required`，密码恢复后续跑。
- 停止和重新创建 worker 后从数据库剩余任务继续。

### Sync integration

- 元数据同步完成后立即返回，不等待正文。
- 全文件夹成功后才更新 `metadataSyncedAt`。
- 正文成功后更新 `bodySyncedAt` 并减少 `pendingBodyCount`。
- 元数据同步和正文下载使用独立 IMAP 会话。
- UID 回退恢复后正文任务不丢失。

### Intelligence

- 元数据邮件不创建依赖正文的任务。
- `mail-hydrated` 后智能任务入队一次。
- 前台和后台同时请求同一邮件不会重复入队。

### Runtime acceptance

- 大批历史邮件先快速完整出现在列表。
- 后台运行时 `pendingBodyCount` 持续下降。
- 应用重启后从剩余未缓存邮件继续。
- 新邮件正文优先于大多数历史邮件补齐。
- 正文下载期间元数据同步仍能及时完成。

## 验收标准

1. 列表元数据同步耗时不再受完整正文体积影响。
2. `metadataSyncedAt`、`bodySyncedAt` 和 `pendingBodyCount` 能准确表达两个同步阶段。
3. 后台正文同步最新优先、单并发、可恢复，并且不会因单封邮件失败停止。
4. 用户打开邮件可以立即提升该邮件正文下载优先级。
5. 密码过期恢复后先完成元数据同步，再自动继续正文同步。
6. 正文成功落库后智能处理幂等触发。
