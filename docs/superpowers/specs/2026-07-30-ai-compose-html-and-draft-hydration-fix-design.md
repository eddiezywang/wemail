# AI 草稿 HTML 外显与草稿编辑正文加载修复设计

## 背景

内嵌 AI 在已有正文上继续修改时，渲染器把编辑器 HTML 原样作为 `currentBody` 发送给模型。模型可能继续在 `draftMarkdown` 中返回 `<p>` 等 HTML 标签，而渲染器随后把该字段按 Markdown 文本转义，最终导致标签作为正文文字显示。

草稿箱列表使用元数据优先响应，列表项可能尚未包含完整正文。当前“编辑草稿”直接把列表项交给写信窗口，只有用户先打开详情页并完成正文加载后，编辑器才会获得完整内容。

## 目标

- AI 可以继续按用户指令修改正文，不限制为仅修改信封字段。
- 当前正文发送给模型前转换为保留段落和换行的纯文本。
- 模型若违反约定并在 `draftMarkdown` 返回 HTML，渲染器进行防御性正文提取，不显示原始标签。
- 点击编辑草稿时主动取得完整草稿正文，不依赖详情页加载副作用。
- 正文加载失败或超时时不打开缺少内容的编辑器，并给出明确错误提示。

## 非目标

- 不改变 AI 对主题、正文、收件人、抄送人、密送人和发送时间的修改权限。
- 不改变草稿列表的元数据优先接口，不把所有完整正文塞入列表响应。
- 不重构邮件详情页正文加载流程。
- 按用户要求不新增测试文件；实现后运行类型检查和已有相关测试。

## 方案

### AI 正文格式边界

渲染器在提交 AI 请求前，将可编辑正文 HTML 转换为纯文本：段落之间保留空行，`<br>` 保留换行，标签和危险内容被移除。签名和引用区域仍由现有保护逻辑剥离，不发送给模型。

AI 返回的 `draftMarkdown` 仍按 Markdown 处理。若内容具有 HTML 标签特征，则先通过同一安全正文提取逻辑转换为纯文本，再执行现有 Markdown 到安全 HTML 的转换。渲染器不直接信任或注入模型返回的 HTML。

因此模型仍可重写正文，但无论返回 Markdown 还是误返回 HTML，编辑器都只接收规范化后的安全 HTML。

### 草稿编辑加载

“编辑草稿”改为异步流程：

1. 检查列表项是否已有完整正文且 `bodyPending` 不为真。
2. 若正文未就绪，调用现有邮件详情 API 获取草稿。
3. 如果返回 `bodyPending`，按现有详情加载节奏进行短间隔重试，直到正文可用、失败或达到超时上限。
4. 正文就绪后才调用 `startCompose`，并使用完整草稿初始化收件人、抄送人、密送人、主题、正文和附件。
5. 加载期间防止重复触发；失败或超时时提示用户重试，不打开空正文编辑器。

回复草稿继续根据 `in_reply_to` 关联原邮件；找不到原邮件时仍可编辑草稿本身，不丢失已保存内容。

## 错误处理与验证

- HTML 转纯文本失败时使用无标签的保守文本结果，不回退为原始 HTML 字符串。
- 草稿加载请求错误、草稿不存在或超时均显示“草稿内容加载失败，请重试”。
- 关闭邮件详情或切换邮件不会中断已经由用户明确触发的草稿加载，但组件卸载后不得继续打开写信窗口。
- 验证现有 AI 草稿测试、邮件面板测试、渲染器类型检查和桌面构建。

## 验收标准

- 在已有 HTML 正文上执行“再抄送 fangfangliu”或其他 AI 指令后，正文不再显示 `<p>`、`</p>`、`<br>` 等标签文字。
- AI 仍可在用户要求时正常改写正文。
- 未提前打开草稿详情页时，直接点击编辑也能带出完整正文。
- 正文未加载成功时不会打开内容缺失的写信窗口。
