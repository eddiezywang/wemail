# 邮件列表双向滑动分页设计方案

## 背景

当前普通邮件列表、所有邮件、标签、搜索和部分虚拟目录只展示有限数量，已有的局部无限查询没有统一接入列表交互。顶部也没有支持保持阅读位置的下拉刷新。

## 目标

1. 收件箱、普通文件夹、所有邮件、用户标签、智能标签、搜索及全部虚拟目录支持连续分页。
2. 向下滚动到底部附近自动加载更旧的 50 封，直到服务端返回没有更多。
3. 顶部继续下拉超过 64px 时，按当前完整条件刷新最新 50 封。
4. 新邮件直接插入顶部，不显示提示，并保持当前滚动位置。
5. 后续分页自动重试 3 次，仍失败时保留已加载列表并显示底部重试入口。
6. 到达末尾显示“已加载全部邮件”。
7. 搜索、筛选、目录或标签变化时清空旧结果，回到顶部重新加载。
8. 查询缓存包含完整目录、虚拟目录、搜索和筛选条件。

## 非目标

- 不改变现有筛选条件语义和邮件排序语义。
- 不添加页码按钮。
- 不在列表组件中用“收件箱前 50 封再前端过滤”实现虚拟目录。
- 不改变 Electron 运行时架构。

## 业务语义

- 所有邮件：当前账户中未删除邮件。
- 星标：is_flagged = 1。
- 稍后处理：snoozed_until_ms 大于当前时间。
- 已计划：使用 outbox 的真实计划发送记录，待发送且计划时间晚于当前时间；不映射为普通邮件。
- 订阅：持久化邮件头中存在 List-Unsubscribe 或 List-ID。
- 待办：使用 todo 表的真实分页结果，仅使用现有智能分析/待办提取结果，未完成分析的不进入。
- 用户标签和智能标签：服务端标签关系匹配。
- 搜索：保留当前关键词解析、搜索范围和筛选条件。

## 统一分页协议

邮件目录统一返回 emails、totalCount、unreadCount、nextCursor 和 hasMore；已计划和待办保留各自的 scheduled/todos 结果结构，但同样返回 totalCount 和 hasMore。

游标分页按 received_at_ms DESC、稳定 message id DESC 排序。游标编码最后一条记录的接收时间和稳定 ID，下一页继续使用完整查询条件。服务端查询使用 limit + 1 判断 hasMore，避免客户端猜测末页。

搜索沿用现有搜索语法，但改为无限查询，每页 50 封，页码或游标请求必须携带完整搜索条件和当前邮件目录范围。

## 前端查询

普通目录和服务端虚拟目录使用无限查询，移除最多保留 4 页的限制，按逻辑邮件 ID 去重，并把服务端 hasMore 映射为 hasNextPage。

搜索改为无限查询，条件变化自然生成新缓存键并从第一批重新加载。

## 顶部下拉刷新

列表位于顶部且继续向下拖动超过 64px 时，使用当前完整查询条件请求最新一批。刷新前记录 scrollTop 和 scrollHeight；新数据按逻辑 ID 去重并插入顶部；DOM 更新后按高度差补偿 scrollTop，使阅读位置不跳动。刷新失败不清空当前列表。已有刷新按钮复用相同刷新动作。

## 列表交互

底部距离不超过 240px 时触发下一页，正在请求时禁止重复触发。底部状态分别显示加载中、加载失败可重试、已加载全部邮件。顶部刷新和底部加载不得并发覆盖同一列表状态。

## 验收标准

1. 普通目录、所有邮件、标签和虚拟目录可连续向下加载。
2. 搜索结果可连续加载，每页 50 封。
3. 所有视图可顶部下拉刷新并保持阅读位置。
4. 新邮件不重复，旧邮件不丢失。
5. 到达末尾显示已加载全部邮件。
6. 分页失败自动重试 3 次后提供当前页重试。
7. 切换筛选、搜索、目录和标签后不复用旧游标。
8. 邮件型虚拟目录来自服务端完整数据源；已计划和待办分别来自 outbox/todo 的服务端分页数据源。
