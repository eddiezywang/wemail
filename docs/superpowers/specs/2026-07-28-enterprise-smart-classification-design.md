# 企业智能分类精简设计

## 背景

当前 WeMail 同时存在三套容易混淆的邮件组织概念：

- 八个互斥系统分类：重要、待处理、订阅、营销、收据、通知、个人、其他。
- 八个内置内容标签：通知、待回复、发布、告警、日报、需求、会议、审批。
- 用户创建并由 AI 自动匹配的智能标签。

侧边栏把系统分类、用户标签和 IMAP 文件夹放在接近的视觉层级中。系统分类数量多、
名称重叠，并且现有“八选一”模型无法表达一封邮件既重要、又待处理、同时还是发票的
常见企业场景。不同岗位需要的主题也差异很大，不适合继续增加全员内置标签。

本设计将固定智能分类收敛为少数高通用能力，把岗位和业务主题交给 AI 动态识别，
并要求用户通过现有通知中心确认后才将稳定主题转为长期智能标签。

## 目标

- 固定系统智能分类只保留“重要、待处理、发票”。
- 三个系统分类可以叠加，不再要求邮件只能归入一个类别。
- AI 可以为单封邮件生成少量临时内容标签。
- AI 发现稳定主题后，通过现有通知中心建议创建长期智能标签。
- 只有用户确认的长期智能标签才进入侧边栏。
- 在 UI、权限和数据模型上明确区分系统智能分类与用户创建标签。
- IMAP 文件夹、WeMail 虚拟视图、系统故障和智能分类保持独立。
- 保留现有用户智能标签、历史回填和反馈学习能力。

## 非目标

- 不创建或修改 IMAP 文件夹。
- 不自动把临时内容标签直接升级为长期智能标签。
- 不提供岗位预设标签包。
- 不保留“订阅、营销、通知、个人、其他”作为用户可见系统分类。
- 不继续把“通知、待回复、发布、告警、日报、需求、会议、审批”作为全员内置标签。
- 不在本次设计中训练或微调底层模型。
- 不重构现有邮箱文件夹的远端操作语义。

## 产品模型

### 邮箱组织层级

WeMail 对用户展示四种明确分离的邮件组织方式：

1. **IMAP 实体文件夹**：由邮箱服务器通过 IMAP `LIST` 返回，例如企业自定义目录。
2. **WeMail 虚拟视图**：本地查询得到的所有邮件、已加星标、已延后、定时发送和待办。
3. **系统智能分类**：WeMail 内置且不可删除的“重要、待处理、发票”。
4. **我的标签**：用户手动创建，或用户确认 AI 建议后创建的长期智能标签。

AI 临时内容标签只附着在邮件上，不构成第五种侧边栏导航对象。

同步失败、服务器故障、AI 处理失败和智能标签建议进入应用消息或运行状态，不创建
“冲突”“服务器故障”等邮件文件夹或智能分类。如果 IMAP 返回同名实体文件夹，
WeMail 可以在邮箱文件夹区域原样展示，但不得把它解释为 WeMail 生成的分类。

### 系统智能分类

三个系统分类是彼此独立的布尔判断，可以同时命中。

#### 重要

“重要”回答的是：这封邮件是否值得当前用户优先关注。

满足下列一种或多种情况，并且与当前用户有直接关系时可以命中：

- 生产故障、安全、合规、资金异常、重大客诉等高风险或高影响事项。
- 正在阻塞关键工作，或明确要求立即关注的高优先级事项。
- 重大项目决策、合同关键变更、核心客户事项或重要发布结果。
- 来自关键角色且正文内容本身具有实质重要性。
- 临近截止且未处理，并可能造成明显业务损失或进度影响的事项。

不得仅凭标题中的“重要”“紧急”等模板词，或仅凭发件人职位判断。普通系统通知、
常规日报、群发公告、普通会议邀请、订阅和仅供抄送知悉的邮件不应自动命中。

#### 待处理

“待处理”回答的是：当前用户读完邮件后，是否能够明确说出自己需要完成的动作。

以下动作可以命中：

- 回复、确认、反馈或补充信息。
- 审批、授权、签署或作出选择。
- 提交材料、修改内容或完成任务。
- 参加会议或确认出席。
- 核查异常、跟进问题或联系相关人员。
- 在明确截止时间前完成尚未完成的事项。

已完成事项的结果通知、仅供知悉的公告、没有后续动作的自动状态更新、行动主体明确
为其他人的邮件，以及只提到工作但没有要求当前用户参与的邮件不应命中。

#### 发票

“发票”只识别可用于开票、报销或财务归档的正式发票材料，包括：

- 电子发票及其附件。
- 开票完成通知和发票下载入口。
- 明确的发票交付邮件。
- 可作为发票凭证的结构化票据信息。

付款回执、银行回单、订单付款确认、报价单、合同、营销优惠、普通付款提醒，以及仅在
正文中提到金额的邮件不属于“发票”。现有发票平台“已上传 / 未上传”等状态继续作为
“发票”的二级业务状态，不升级为新的系统分类。

### 组合语义

| 组合 | 含义 | 示例 |
| --- | --- | --- |
| 重要 + 待处理 | 需要优先行动 | 生产故障要求立即确认处置 |
| 仅重要 | 需要优先知悉 | 重大组织调整或关键项目决策结果 |
| 仅待处理 | 常规行动 | 确认普通会议时间或补交一般材料 |
| 发票 + 待处理 | 需要处理发票事项 | 收到发票并要求本周完成报销 |
| 三者均未命中 | 普通知悉邮件 | 常规通知、日报或订阅内容 |

“供知悉”是三者均未命中时的自然状态，不作为第四个系统标签，也不单独占用侧边栏。

## 临时内容标签

智能处理可以为每封邮件生成零到三个临时内容标签，例如“生产告警”“AIMC 版本交付”
或“项目周报”。这些标签帮助用户理解邮件主题，并为长期智能标签建议积累证据。

生成规则：

- 名称使用二至八个汉字为主的短语。
- 标签描述稳定业务主题，不照抄邮件标题。
- 不生成“重要、待处理、发票”等系统分类。
- 不生成“通知、其他、个人”等缺乏筛选价值的宽泛标签。
- 不把姓名、具体日期、单次版本号等易变化信息直接作为标签。
- 低置信度、只依赖单一标题或无法说明业务主题时不生成标签。

临时内容标签使用中性虚线视觉，只出现在邮件列表和详情中。它们不得未经用户确认进入
侧边栏，也不得被当作 IMAP 文件夹或长期智能标签使用。

## 主题候选池与归一化

每个账号维护独立的主题候选池。候选主题至少包含：

- 稳定的内部 `topicId`。
- 当前展示名称及同义名称。
- 命中邮件数、线程数和发件人分布。
- 首次出现时间和最近出现时间。
- 用户反馈与抑制状态。
- 是否已经转为长期智能标签，以及对应的长期标签 ID。

归一化按以下顺序处理：

1. 清理日期、版本号、姓名等一次性信息。
2. 使用规范名称和同义名称匹配已有主题。
3. 结合实际邮件样本判断是否语义相同。
4. 无可靠匹配时创建新的候选主题。

仅名称相似不足以合并主题；实际命中邮件也必须表达相近的业务意图。已有长期智能标签
覆盖某个主题时，候选池不得继续生成同义创建建议。

## 建议长期智能标签

候选主题同时满足以下条件时，可以生成一次长期智能标签建议：

- 最近三十天至少命中五封邮件。
- 至少跨两个邮件线程或两个发件人。
- 主题不是明显的一次性事件。
- 与现有长期智能标签没有明显重叠。
- 该主题对筛选、查找或批量处理邮件具有实际价值。
- 当前没有同一 `topicId` 的待处理建议。
- 用户没有对该主题或同义主题选择“不再建议”。

以上阈值作为初始产品默认值，并应通过可注入配置或服务常量实现，便于测试和后续调整。

### 通知中心交互

建议复用现有应用消息和通知中心能力，不引入独立收件箱。通知示例：

> 发现 12 封与“AIMC 版本交付”相关的邮件。是否创建智能标签？创建后，AI 会继续
> 自动归类类似邮件。

通知提供以下操作：

- **查看邮件**：预览本次建议的代表性样本。
- **创建**：使用建议名称和描述创建长期智能标签。
- **编辑后创建**：修改名称和描述后创建。
- **暂不创建**：关闭本次建议；出现明显新增样本后允许再次建议。
- **不再建议**：抑制该主题及其同义主题的后续建议。

通知中心保留“待确认、已创建、暂不创建、不再建议、创建失败”等状态。处理后的记录
继续可追溯，至少展示建议主题、样本数量、处理结果和处理时间。

用户确认创建后才执行以下动作：

1. 创建现有模型中的用户智能标签。
2. 关联建议通知、`topicId` 与新标签 ID。
3. 启动现有历史邮件回填流程。
4. 在侧边栏“我的标签”分组中显示新标签。

## 用户纠偏

### 系统智能分类

- 用户可以直接开启或关闭“重要”和“待处理”。
- 用户可以标记或取消“发票”，但取消不得删除邮件附件或发票平台记录。
- 人工选择优先于当前 AI 结果，并记录为后续判断样本。
- 后台重算不得覆盖仍然有效的人工选择。

### 临时内容标签

- 用户可以从当前邮件移除错误标签。
- 用户可以提出更准确的展示名称。
- 移除记录为“该邮件不属于该主题”的负样本。
- 修改名称只作为主题命名建议，不立即全局重命名。
- 大量持续移除应降低主题建议优先级，必要时自动停止建议。

### 长期智能标签

继续复用现有“移入 / 移出”、备注、反馈记录、批量 Prompt 优化和历史回填能力。
用户自建标签与用户确认 AI 建议后创建的标签在运行时语义相同，但保留不同的创建来源
用于审计。

## UI 设计

### 视觉方向

采用精炼、克制的企业工具风格，延续 WeMail 现有暖白背景和珊瑚强调色，不引入新的
高饱和视觉体系。重点不是装饰，而是让用户一眼理解所有权和可管理性。

采用已确认的 A“独立双分组”方案：

```text
所有邮件

智能分类
  ◆ 重要
  ✓ 待处理
  ▣ 发票

我的标签
  ◇ AIMC 交付
  ◇ 字节合作
  + 创建智能标签
```

### 系统智能分类

- 分组标题为“智能分类”。
- 使用珊瑚色和实心或专属语义图标。
- 不提供重命名、编辑描述或删除菜单。
- 可以展示未读数或匹配数。
- 详情页标签使用相同系统视觉语义。

### 我的标签

- 分组标题为“我的标签”。
- 使用蓝灰色和描边标签图标。
- 悬停或聚焦后提供编辑、学习记录和删除入口。
- 保留“创建智能标签”入口。
- 用户手动创建和确认 AI 建议创建的标签都进入此分组。

### 可访问性与交互

- 不只依赖颜色区分来源，同时使用分组标题、实心或描边图标及不同管理能力。
- 当前项继续使用清晰的选中背景和侧边强调线。
- 键盘聚焦时必须显示管理入口和焦点样式。
- 相同邮件允许在多个系统分类中重复计数。
- 未确认临时标签不得出现在侧边栏。
- IMAP 自定义文件夹继续位于邮箱文件夹区域，不混入两个智能分组。

## 服务边界与数据流

建议将职责拆分为四个可独立测试的单元：

- `SystemClassificationProcessor`：输出三个独立系统分类结果。
- `ContentTopicProcessor`：生成单封邮件的临时内容标签。
- `TopicCandidateRepository`：持久化候选主题、同义关系、统计、反馈和抑制状态。
- `SmartTagSuggestionService`：评估建议门槛，写入通知中心并处理用户决定。

核心数据流：

```text
IMAP 收到邮件
  -> SystemClassificationProcessor
  -> ContentTopicProcessor
  -> TopicCandidateRepository 聚合
  -> SmartTagSuggestionService 检查门槛
  -> 通知中心请求用户确认
  -> 用户确认
  -> 现有用户智能标签创建与历史回填
```

系统分类建议使用独立结构表达：

```ts
interface SystemClassificationResult {
  important: ClassificationSignal;
  actionRequired: ClassificationSignal & { actions?: string[] };
  invoice: ClassificationSignal & { evidence?: string[] };
  contentTags: ContentTopicTag[];
}

interface ClassificationSignal {
  matched: boolean;
  confidence: number;
  reason: string;
  source: "ai" | "rule" | "user";
}
```

“待处理”应优先复用回复决策、待办提取和行动主体判断。“发票”应优先结合附件类型、
文件名、正文结构和现有发票识别能力。三个判断可以在一次模型响应中生成，但持久化和
重试语义必须独立，避免单项失败使全部结果不可用。

## 存量迁移

### 系统分类

- “重要”和“待处理”迁移为独立信号。
- “收据”在 UI 中改名为“发票”，但历史“收据”结果不得直接全部迁移为发票。
- “订阅、营销、通知、个人、其他”退出用户界面。
- 旧类别可在过渡期保留为后台兼容字段或弱信号，用于降噪、摘要和读取旧数据。
- 新邮件使用新结构；历史邮件通过后台任务逐步重算。

### 内置内容标签

“通知、待回复、发布、告警、日报、需求、会议、审批”不再作为固定内置标签定义。
它们可以作为临时内容标签的规范名称或归一化种子，但必须遵循候选池和用户确认规则，
不得自动进入侧边栏。

### 用户标签

所有现有用户智能标签原样保留，继续使用稳定标签 ID、现有邮件关系、回填记录和反馈
历史。迁移只调整它们在侧边栏中的分组和视觉归属，不重建标签或丢失关系。

## 异常处理与幂等

- 系统分类整体失败时，邮件仍正常进入“所有邮件”，不写入半成品结果。
- 单项分类失败时，其他成功项可以保存，失败项独立重试。
- 内容标签或主题聚合失败不得影响系统分类、同步或邮件阅读。
- 建议使用 `accountId + topicId` 作为待处理通知幂等键。
- 同一主题存在待处理建议时不得重复通知。
- 创建长期标签失败时，通知保持可重试状态，不提前显示侧边栏标签。
- 用户确认时主题已经合并，应展示新的规范名称和样本数量后再创建。
- 用户删除长期标签后，移除标签关系和侧边栏入口，但保留建议、反馈和学习历史。
- 用户选择“不再建议”后，同义主题也必须命中抑制规则。
- IMAP、服务器、AI 或后台任务故障进入应用消息或技术日志，不生成文件夹或分类。

## 测试策略

### 单元测试

- 重要、待处理和发票规则的正例、反例及组合命中。
- 发票识别排除付款回执、银行回单、报价单和普通付款提醒。
- 临时内容标签数量、长度、禁用名称和一次性信息清理。
- 同义主题合并与相似名称但不同业务意图的不合并。
- 三十天、五封、跨线程或发件人的建议门槛。
- 暂不创建、不再建议、同义抑制和重复通知幂等。
- 人工覆盖不被后台重算覆盖。

### 服务与 API 测试

- 系统分类结果支持多项同时为 `matched=true`。
- 单项处理失败不会丢失其他分类结果。
- 用户确认通知后原子创建长期标签并关联 `topicId`。
- 创建失败不会产生孤立标签或提前显示的侧边栏记录。
- 历史回填只在用户确认后启动。
- 账号之间的候选主题、抑制规则和建议完全隔离。

### Renderer 测试

- 侧边栏分别渲染“智能分类”和“我的标签”。
- 系统分类没有编辑和删除入口。
- 用户标签支持键盘和鼠标打开管理入口。
- 临时内容标签只出现在邮件列表和详情。
- 分组区别不只依赖颜色。
- 订阅、营销、通知、个人、其他不再出现在侧边栏。
- 用户现有标签在迁移后继续可见并可导航。

### 端到端验收

- 一封紧急发票邮件可以同时进入重要、待处理和发票。
- 普通付款成功回执不会进入发票。
- 稳定主题达到门槛后只产生一条可追溯通知。
- 临时主题未经确认不会进入侧边栏。
- 用户查看样本并确认后，标签进入“我的标签”并开始回填。
- 用户选择“不再建议”后，同义主题不会再次出现。
- IMAP 自定义文件夹仍在邮箱文件夹区域正常显示。
- 同步失败通过应用消息或错误状态反馈，不创建“服务器故障”目录。

## 完成标准

- 用户可见固定系统分类仅有重要、待处理和发票。
- 三个系统分类支持任意组合命中和人工纠偏。
