# WeMail 通讯录部门成员聚合设计

## 背景

当前企业通讯录左侧展示可展开的部门树，右侧联系人表只按所选部门的 `department_id` 精确查询直属员工。对于“武汉研发中心”这类主要包含下级部门的父部门，用户选中后会看到 0 位联系人，并被要求继续逐层展开和选择下级部门。这使组织层级与员工数据看起来没有关联。

本次调整后，左侧仍只负责浏览组织层级；选中任一部门时，右侧展示该部门直属员工以及全部下级部门员工。

## 目标

- 选择部门后，展示该部门及全部后代部门的联系人。
- 联系人总数、分页、当前页选择和批量写信基于同一聚合结果。
- 保持“全部同事”和全局搜索的现有行为。
- 保持通讯录全量快照同步，不引入会随同步次数累积的数据。
- 在大型组织树和全量联系人快照下保持可预测的 SQL 性能。

## 非目标

- 不把员工渲染为左侧组织树节点。
- 不改变 Coremail 登录、部门遍历或联系人拉取协议。
- 不增加联系人或部门的编辑、删除、导出和权限管理能力。
- 不改变搜索框的全局搜索语义。
- 不增加部门闭包表、祖先映射缓存或其他需要跨同步维护的数据结构。

## 方案选择

采用 SQLite 递归 CTE，在查询时计算“当前部门及其全部后代部门”的 ID 集合，并用该集合过滤联系人。

未采用的方案：

- `department_path` 前缀匹配：依赖路径文本格式，容易受到部门重名、路径分隔符和名称变更影响。
- 前端递归加载部门并并发查询联系人：请求数量随部门规模增长，难以保证总数、排序和分页一致。
- 持久化部门闭包表：读取快，但会增加全量同步写入和清理复杂度；若维护边界出错，还可能形成历史关系堆积。本次查询规模不需要引入该结构。

## 数据流

1. 用户在左侧选择一个部门。
2. 页面在联系人查询中传递所选 `departmentId`，并明确请求包含下级部门。
3. `DirectoryService` 将查询选项传给 `DirectoryRepository`。
4. 仓储使用递归 CTE 从 `directory_departments` 当前账号、当前部门开始，沿 `parent_id` 查找全部后代部门。
5. 联系人查询通过 `department_id IN (递归结果)` 完成过滤，并继续使用既有姓名排序、分页和搜索逻辑。
6. 联系人列表查询与计数查询使用相同的部门集合语义，保证页数和结果一致。

全局搜索仍不携带部门过滤。清空搜索后恢复当前选中部门的聚合联系人结果。

## API 与类型

联系人查询选项增加显式布尔语义：

```ts
interface DirectoryContactQueryOptions {
  departmentId?: string;
  includeDescendants?: boolean;
  limit?: number;
  offset?: number;
}
```

页面选择部门时传递 `includeDescendants: true`。其他既有调用方不传该字段时继续执行精确部门查询，以避免无意改变 Agent 工具或其他内部调用的行为。

HTTP API 和 Electron preload IPC 都透传该选项。服务层不自行展开部门，部门范围计算集中在仓储查询中。

## SQL 与性能设计

部门范围使用受账号约束的递归 CTE，概念结构如下：

```sql
WITH RECURSIVE department_scope(id) AS (
  SELECT id
  FROM directory_departments
  WHERE account_id = ? AND id = ?

  UNION

  SELECT child.id
  FROM directory_departments child
  JOIN department_scope parent ON child.parent_id = parent.id
  WHERE child.account_id = ?
)
SELECT ...
FROM directory_contacts
WHERE account_id = ?
  AND department_id IN (SELECT id FROM department_scope)
ORDER BY name
LIMIT ? OFFSET ?;
```

性能约束：

- 递归的锚点和子节点查询始终包含 `account_id`，禁止跨账号扫描。
- 复用现有部门主键以及 `idx_directory_departments_parent (account_id, parent_id, name)` 索引。
- 复用现有 `idx_directory_contacts_department (account_id, department_id, name)` 索引支持联系人过滤和排序。
- 本次不新增索引迁移；只有 `EXPLAIN QUERY PLAN` 或真实规模基准证明现有访问路径不足时，才另行评估普通索引。
- 列表与计数在数据库内完成，不把完整联系人或完整组织树加载进渲染器内存。
- 不为每个后代部门分别执行联系人 SQL，避免 N+1 查询。
- 搜索场景沿用现有全局 FTS/短词查询，不额外执行部门递归。

## 全量同步与数据生命周期

现有 `replaceSnapshot` 在单个事务内依次删除当前账号的联系人 FTS、联系人和部门数据，再写入本次完整快照。本次设计保持该边界不变：

- 每次成功同步后，数据库只保留当前账号的最新部门和联系人快照。
- 递归 CTE 只读取当前快照，不生成或持久化派生部门关系。
- 不新增按同步批次保存的部门、联系人或祖先关系记录。
- 同步失败时继续保留上一次成功快照，不写入半成品数据。
- 新增索引时使用固定结构，索引条目随全量删除和替换的数据一起更新，不会按同步次数堆积业务记录。

因此，查询成本取决于当前组织树和当前联系人规模，而不是历史同步次数。

## 界面行为

- 左侧部门树交互和懒加载保持不变。
- 点击父部门后，右侧标题仍显示该部门名称。
- “共 N 位联系人”统计该部门及全部下级部门的去重联系人记录。
- 空状态改为“该部门及下级部门暂无成员”。
- 搜索期间保留树的视觉选中状态，但结果仍为全局搜索；清空搜索后回到所选部门聚合结果第一页。
- 切换部门时继续清空已选联系人并回到第一页。

## 数据一致性与异常处理

- 部门不存在或不属于当前账号时，递归范围为空，返回 0 位联系人，不回退到全通讯录。
- 若组织数据意外存在环，使用 `UNION` 去重或等效的已访问保护，确保递归终止；实现时不得使用无环保护的无限递归方案。
- 联系人只保存一个当前 `department_id`，因此聚合结果不会因多条祖先路径重复；查询仍应保持稳定的联系人行唯一性。
- 列表查询和计数查询必须共享相同的范围条件，避免空页或页数错误。
- 通讯录刷新完成后继续失效部门和联系人查询缓存，使聚合结果切换到新快照。

## 测试与验证

### 仓储测试

- 选择叶子部门时只返回该部门直属员工。
- 选择父部门时返回直属员工、子部门员工和多层后代部门员工。
- 不返回兄弟部门、祖先部门或其他账号员工。
- 聚合列表与聚合计数一致。
- 聚合查询保持姓名排序、分页和 offset 行为。
- 不传 `includeDescendants` 时保持精确部门过滤。
- 不存在的部门返回空结果。
- 异常环形部门关系不会导致查询失控。

### 服务、API 与 IPC 测试

- `includeDescendants` 从渲染器 API 依次透传到 HTTP 或 Electron IPC、服务和仓储。
- 旧调用方省略新字段时行为不变。

### 渲染器测试

- 选择父部门时联系人请求携带 `includeDescendants: true`。
- 清空搜索后恢复父部门聚合查询。
- 聚合结果为空时显示新的空状态文案。
- 分页、选择联系人和批量写信继续使用当前返回结果。

### 性能验证

- 检查迁移后的索引定义，确认部门递归和联系人过滤的关键列已覆盖。
- 使用接近真实规模的部门与联系人数据执行 `EXPLAIN QUERY PLAN`，确认没有对每个部门执行独立联系人全表扫描。
- 连续执行多次全量快照替换，确认部门、联系人和 FTS 行数只反映最新快照，不随同步次数增长。
- 运行 `npm run typecheck`、`npm run typecheck:server`、`npm run test:server` 和 `npm run test:renderer`；涉及 preload 后运行 `npm run typecheck:desktop` 和 `npm run build:desktop`。

## 验收标准

- 选中“武汉研发中心”后，右侧能看到其各研发室等所有下级部门员工。
- 选中叶子部门时仍只显示该叶子部门员工。
- “全部同事”和全局搜索行为无回归。
- 联系人总数与分页结果一致。
- 多次全量同步不会新增历史快照或派生关系记录，不会因同步次数增加而放大查询数据量。
- 聚合查询使用单次数据库查询完成部门范围过滤，不产生前端请求风暴或服务端 N+1 SQL。
