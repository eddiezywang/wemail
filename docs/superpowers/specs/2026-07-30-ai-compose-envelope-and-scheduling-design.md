# WeMail AI 草稿信封字段与建议发送时间设计

## 背景

写信窗口底部的内嵌 AI 当前主要生成或改写主题和正文。虽然草稿结果已经具备有限的 `to`、`cc` 字段，但这条链路不会主动读取企业通讯录来解析用户提到的同事，也不能表达收件人增删或替换语义，更不能把“明天上午九点发送”转换成可供用户确认的发送时间。

右侧 WeMail AI 已有通讯录查询、草稿保存和定时发送工具，但内嵌 AI 草稿是更轻量的写信体验。本次只扩展内嵌 AI 草稿，使用户可以用一句自然语言同时生成内容、设置邮件信封字段并得到建议发送时间。

## 目标

- AI 草稿能够生成或修改主题和正文。
- AI 能识别收件人、抄送人和密送人的新增、替换与删除意图。
- 服务端使用当前账号的企业通讯录把同事姓名解析为准确邮箱，不允许模型猜测员工地址。
- 默认保留已有地址并追加 AI 识别的人员；只有用户明确说“改为”“只发给”“移除”等操作时才替换或删除。
- AI 能把明确的自然语言时间解析成带时区的未来发送时间，并填入写信窗口供用户确认。
- 生成草稿不会保存邮件、创建定时发送任务或自动发送；只有用户点击发送或定时发送后才执行现有流程。
- 保持现有签名、引用正文、附件和正文版本行为安全可预测。

## 非目标

- 不扩展或重做右侧 WeMail AI 的工具能力。
- 不让 AI 自动发送邮件或在生成草稿时直接创建定时任务。
- 不新增通讯录编辑、联系人创建或组织架构管理能力。
- 不让 AI 添加、删除或修改附件。
- 不把完整企业通讯录、账号凭据、Cookie、Coremail `sid` 或其他会话信息发送给模型。
- 不让正文版本切换回滚收件人、抄送人、密送人或建议发送时间。

## 方案选择

采用“结构化 AI 草稿意图 + 服务端通讯录解析”的两阶段方案。

第一阶段由模型输出主题、正文、人员操作和发送时间意图。人员只使用用户输入中的姓名、邮箱或其他定位信息，模型不得补全或猜测邮箱。第二阶段由服务端使用当前账号的 `DirectoryService` 解析企业联系人，并对人员操作与时间进行确定性校验。全部校验通过后，服务端返回一个可原子应用到写信窗口的安全补丁。

未采用的方案：

- 先搜索一批联系人并全部放入模型提示词：候选可能遗漏，组织规模大时上下文膨胀，也会增加同名误选风险。
- 让内嵌 AI 使用右侧 Agent 的多轮工具循环：能力完整，但会显著增加延迟、状态管理和界面复杂度，不符合内嵌写作入口的轻量定位。
- 仅在渲染器解析模型文本：无法安全复用服务端通讯录与时间校验，也容易形成跨端不一致。

## 架构与组件边界

### ComposeDraftInterpreter

负责调用模型并把用户指令解释为结构化草稿意图。输入包含操作模式、用户指令、当前主题、当前正文、当前信封字段、客户端当前时间及时区，以及回复场景的原邮件上下文。

输出包含：

- `subject` 和 `draftMarkdown`；
- `recipientChanges.to`、`recipientChanges.cc`、`recipientChanges.bcc`；
- 每组人员操作的 `operation`，取值为 `add`、`replace` 或 `remove`；
- 待解析的人员引用，包括用户原始姓名、显式邮箱、部门或职务提示；
- 可选的发送时间意图，包括用户原始表达与解析所需字段；
- 模型认为信息不足时的澄清问题。

该单元只解释意图，不访问通讯录，不创建草稿或发送任务。

### ComposeRecipientResolver

负责使用当前账号的 `DirectoryService` 解析人员引用：

- 用户给出合法邮箱时可以直接规范化使用；
- 用户给出同事姓名时查询企业通讯录；
- 唯一匹配时返回规范化的姓名与邮箱；
- 多个候选时返回包含部门或职务的消歧问题；
- 未找到或联系人没有可用邮箱时返回澄清问题；
- 不得因远端通讯录不可用而猜测邮箱。

该单元不调用模型，不修改写信窗口状态。

### ComposeEnvelopePatchValidator

负责确定性校验并生成最终补丁：

- 邮箱按小写比较去重，同时保留第一个有效显示名；
- `add` 与现有地址合并；
- `replace` 和 `remove` 必须能从用户原始指令中验证明确操作措辞，否则降级为 `add`；
- 删除只针对准确解析到的已有邮箱；
- 时间必须解析为带时区的未来 ISO 时间；
- 模糊时间、过去时间以及夏令时不存在或重复的本地时间进入澄清流程。

验证成功后返回一次性应用的 `ComposeDraftPatch`，验证失败时不返回部分补丁。

## 接口与类型

内嵌 AI 草稿请求增加当前信封和时间上下文：

```ts
interface ComposeDraftRequest {
  operationType: "NEW" | "REPLY";
  intent: string;
  emailId?: string;
  currentTo?: string[];
  currentCc?: string[];
  currentBcc?: string[];
  currentSubject?: string;
  currentBody?: string;
  targetLanguage?: string;
  styleId?: string;
  clientNow: string;
  clientTimeZone: string;
}
```

成功结果扩展为完整补丁：

```ts
interface ComposeDraftPatch {
  subject?: string;
  draftMarkdown: string;
  to?: string[];
  cc?: string[];
  bcc?: string[];
  suggestedSendAt?: string;
  suggestedSendTimeZone?: string;
  suggestedSendSourceText?: string;
  changeSummary: string[];
}
```

现有 `needsClarification` 状态继续复用，但问题可以来自模型解释、通讯录解析或时间校验。一次请求只应用完整、已验证的补丁；任何阻塞性歧义都返回澄清状态并保持写信窗口原内容不变。

账号身份不得由渲染器任意指定。服务端继续从当前请求上下文或当前邮箱账号边界确定通讯录账号，确保跨账号联系人隔离。

## 数据流

1. 用户在内嵌 AI 输入“明天上午九点发给张三，抄送李四，通知项目上线”。
2. 渲染器提交当前主题、正文、收件人、抄送人、密送人、客户端时间和 IANA 时区。
3. `ComposeDraftInterpreter` 生成正文、主题、人员操作和时间意图。
4. `ComposeRecipientResolver` 使用当前账号企业通讯录解析张三和李四。
5. `ComposeEnvelopePatchValidator` 验证人员操作、去重地址并把时间转换为未来 ISO 时间。
6. 唯一匹配且时间明确时，接口返回完整 `ComposeDraftPatch`。
7. 渲染器一次性应用正文、主题、信封字段和建议发送时间，并显示变更摘要。
8. 用户检查并可继续修改所有字段。
9. 用户点击“定时发送”后，才复用现有保存草稿和 `ScheduledSendService` 流程创建定时任务。

如果人员或时间存在歧义，第 4 或第 5 步返回澄清问题。用户回答后，内嵌 AI 延续现有澄清对话，将原始请求、问题和用户答案一起重新提交。

## 人员字段语义

- 默认操作为 `add`，保留当前字段并追加新人员。
- “发给张三”“抄送李四”“也告诉王五”均视为追加。
- “收件人改为张三”“只发给张三”允许替换对应字段。
- “移除李四”“不要抄送王五”允许删除准确匹配的人员。
- 未明确指定收件人、抄送人或密送人的人员不得跨字段移动。
- 同一邮箱不能同时因重复解析而出现多次；若用户明确把同一人放在多个不同字段，校验器应提示冲突，不擅自决定优先级。
- 回复和回复全部场景沿用当前初始化的收件人，除非用户明确要求变更。

## 发送时间语义

- 渲染器每次请求发送 `clientNow` 和 `clientTimeZone`，避免服务端系统时区影响“明天”“上午九点”等相对时间。
- 解析结果保存为 ISO 时间，同时保留 IANA 时区和用户原始表达供界面展示与审计。
- “明天上午九点”“7 月 31 日 14:30”可以形成建议时间。
- “下周找时间”“晚点发”以及缺少必要日期或时刻的信息必须澄清。
- 解析结果不在未来时必须澄清，不自动顺延到下一天或下一年。
- 生成动作只设置写信窗口内存中的建议时间，不保存数据库记录。
- 用户修改或清除建议时间后，以用户选择为准；后续正文优化不会恢复旧建议时间。

## 界面行为

- AI 成功后一次性更新主题、正文、收件人、抄送人和密送人。
- 人员继续使用现有 `DirectoryRecipientInput` 标签交互，显示姓名并保留准确邮箱。
- AI 填入抄送或密送时自动展开 CC/BCC 区域。
- 识别到发送时间后，在发送按钮附近显示“计划：明天 09:00”或等价的本地化文本，并提供修改和清除入口。
- 存在建议发送时间时，主操作显示“定时发送”；用户点击后才调用现有定时发送流程。
- 应用成功后显示简短变更摘要，例如“已生成正文；新增收件人张三；新增抄送人李四；建议明天 09:00 发送”。
- 用户手动修改字段不会触发自动再生成。
- 正文版本切换只管理可编辑正文，不回滚信封字段或建议发送时间。
- 继续使用当前签名和引用保护，AI 只替换可编辑正文区域。

## 错误与边界处理

- 通讯录重名时列出有限候选的姓名、部门和职务，要求用户消歧。
- 通讯录未命中时提示补充姓名、部门或直接输入邮箱。
- 远端通讯录不可用且本地缓存无结果时，返回非破坏性的澄清提示，不弹出误导性的生成成功状态。
- 模型、通讯录或时间解析失败时，写信窗口保持全部原值。
- 最终补丁在渲染器中原子应用，避免正文已改变但人员或时间没有改变的半完成状态。
- 已存在的无效地址不由 AI 静默删除；发送前继续走现有地址校验。
- 模型不能通过结构化输出请求发送、保存草稿或操作附件；未知字段被 schema 拒绝。
- 审计日志只记录操作类型、匹配数量和错误类别，不记录邮件正文、完整提示词、凭据或会话信息。

## 测试与验证

### 解释器与 schema 测试

- 新邮件可以同时生成主题、正文、收件人、抄送人和建议时间。
- 默认人员操作为 `add`。
- “只发给”“改为”“移除”等明确措辞分别产生 `replace` 或 `remove`。
- 模型结果不能包含发送、保存或附件操作。
- 非法结构化输出被拒绝且不产生部分结果。

### 通讯录解析测试

- 唯一姓名匹配返回准确姓名和邮箱。
- 同名联系人返回带部门或职务的消歧问题。
- 未找到、无邮箱和通讯录不可用均不猜测地址。
- 显式外部邮箱无需通讯录命中即可使用。
- 不同账号的联系人严格隔离。

### 补丁校验测试

- AI 新人员默认与现有地址合并并去重。
- “只发给张三”才替换已有收件人。
- “移除李四”只删除准确匹配的已有地址。
- 未验证到明确变更措辞的 `replace/remove` 降级为 `add`。
- 同一邮箱跨字段冲突进入澄清，不静默选择字段。
- 任一步失败时不返回或应用部分补丁。

### 时间测试

- “明天上午九点”按客户端时区解析成未来 ISO 时间。
- 过去时间、模糊时间、无效时区和夏令时异常时间进入澄清。
- 生成成功只设置建议时间，不创建 `mail_outbox_items` 记录。
- 用户点击定时发送后才调用现有计划发送接口。

### 渲染器测试

- 完整补丁一次性更新主题、正文、收件人、抄送人、密送人和建议时间。
- AI 填入 CC/BCC 时自动展开对应区域。
- 变更摘要准确展示实际应用的修改。
- 清除或修改建议时间后发送按钮状态正确更新。
- 正文版本切换不改变人员和时间。
- 签名、引用正文和附件保持不变。
- 澄清或接口失败时所有原字段保持不变。

- `npm run typecheck`
- `npm run typecheck:server`
- `npm run typecheck:desktop`
- `npm run test:server`
- `npm run test:renderer`
- `npm run build:desktop`

## 验收标准

- 输入“明天上午九点发给张三，抄送李四，通知项目上线”后，唯一匹配的企业联系人被填入正确字段，主题和正文生成完成，并显示建议发送时间。
- 写信窗口已有人员时默认保留并追加；只有明确替换或删除指令才改变已有人员。
- 同名、未找到联系人或模糊时间不会被猜测，而是通过现有 AI 澄清交互询问用户。
- AI 生成本身不会保存草稿、创建定时发送记录或发送邮件。
- 用户点击定时发送后才执行现有保存与调度流程。
- 签名、引用正文、附件、账号隔离和现有手工收件人输入行为无回归。
