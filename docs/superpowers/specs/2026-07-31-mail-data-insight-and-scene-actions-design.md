# 邮件数据洞察与默认场景动作设计

## 背景

当前单封邮件摘要可能在正文尚未完整缓存时生成。正文随后补齐，已有成功摘要任务仍会因为 `(email_id, type)` 唯一约束而保持完成状态，导致基于旧正文的摘要长期留存。监控报表邮件还会被普通摘要逻辑处理，模型可能把主题、业务名称或收件人信息误当作正文重点，而没有识别表格中的指标、异常和趋势。

WeMail 已经具备两项可复用能力：

- Agent 可以绑定当前邮件、接收预填指令并在用户确认后执行。
- Design Artifact 流程可以把结构化数据生成可信的图表或洞察报告。

本设计修复摘要与正文版本不一致的问题，将监控报表邮件升级为数据洞察，并用统一的默认场景动作机制同时承载“生成图表”和“上传至发票平台”。

## 目标

1. 摘要必须基于当前完整正文，正文变化后旧摘要不能继续展示。
2. 监控或报表邮件展示核心指标、异常点和有证据支持的趋势判断，而不是把业务名称当成邮件内容。
3. 只有监控/报表邮件中存在可靠、可绘制的数据时，才显示“生成图表”。
4. 点击“生成图表”只打开当前邮件的 Agent 会话并预填指令，不自动发送或生成产物。
5. “生成图表”和“上传至发票平台”使用同一套默认场景动作机制，便于后续增加其他场景。
6. 保持普通邮件摘要和现有发票上传安全确认链路兼容。

## 非目标

- 不在摘要阶段直接生成图表或 Design Artifact。
- 不为监控邮件增加第二个独立 AI 处理器。
- 不根据单个数字、日期、订单号或普通通知显示图表动作。
- 不让模型自由生成按钮、执行指令或高风险操作。
- 不在本次设计中增加“创建日程”“提交报销”等新场景。

## 总体方案

继续使用现有单封邮件摘要处理器，并向后兼容地扩展摘要结果。摘要处理器负责识别监控数据邮件和生成有证据约束的数据洞察。服务端的默认场景动作目录根据邮件事实、摘要识别结果和业务状态决定可显示的动作。前端使用一个通用组件渲染动作，并将受控的动作指令预填到当前邮件的 Agent 会话。

```text
邮件正文补齐或变化
  -> 计算正文版本与内容指纹
  -> 失效不匹配的旧摘要
  -> 生成当前版本摘要/数据洞察
  -> 服务端解析默认场景动作
  -> 邮件详情展示摘要或数据洞察
  -> 用户点击动作
  -> 打开当前邮件 Agent 会话并预填受控指令
  -> 用户修改或发送
  -> Agent 复用现有图表或发票安全执行链路
```

## 摘要正文一致性

### 输入版本

邮件仓储已经维护 `bodyVersion`。摘要任务执行时记录：

- `bodyVersion`：生成摘要时使用的正文版本。
- `contentFingerprint`：规范化后的主题、发件人、正文文本和正文 HTML 降级文本的稳定指纹。

这两个值进入摘要质量元数据，不记录原始正文。

### 失效与重新生成

正文补齐或更新后：

1. 比较当前 `bodyVersion`、`contentFingerprint` 与已存摘要元数据。
2. 不一致时将已有摘要标记为陈旧，重置对应摘要任务并重新排队。
3. 前端不展示已经确认陈旧的摘要。
4. 新摘要成功后原子替换旧结果。

历史摘要没有版本元数据时采用兼容策略：如果当前邮件正文包含明显的结构化数据，而历史摘要声称正文为空、只复述主题或缺少正文证据，则触发一次重算。该兼容分支只用于迁移旧结果，新结果写入版本元数据后不再重复触发。

### 空正文保护

摘要处理前区分两种状态：

- 正文仍未缓存：延迟任务，不生成成功摘要。
- 正文已确认缓存但确实为空：允许生成简短的空内容说明。

如果传给模型的正文存在可用文本，则拒绝接受“正文为空”或只复述主题/参与人的输出，并进入一次受控重试。日志只记录正文长度、上下文来源和错误码，不记录正文内容。

## 监控数据洞察

### 摘要结果扩展

现有 `SummaryResult` 保留 `headline`、`details`、`actions`、`bullets` 和 `actionItems`，新增可选的 `dataInsight`：

```ts
interface SummaryDataInsight {
  kind: "monitoring_report";
  metrics: Array<{
    label: string;
    value: string;
    context?: string;
  }>;
  findings: Array<{
    kind: "fact" | "anomaly" | "trend";
    text: string;
  }>;
  evidenceLevel: "snapshot" | "time_series";
  chartRecommended: boolean;
  chartReason?: string;
}
```

约束：

- `metrics` 最多 4 项，只保留正文中可直接核验的数值和单位。
- `findings` 最多 3 项。
- `snapshot` 只能生成事实或异常描述，不能声称存在趋势。
- `trend` 必须由多个时间点支持。
- 不推测异常原因；正文未给出原因时明确不下原因结论。
- `chartRecommended` 只有在邮件属于监控/报表场景，并且正文存在可靠表格、时间序列或多项可比较指标时才为 `true`。
- 数字、日期、比例、模型名称和业务字段必须忠实保留，不得根据主题或收件人补造。

### 提示与校验

摘要提示明确划分主题、发件人、收件人和正文边界，并要求先判断正文是否为监控/报表数据。输出后执行确定性校验：

- 指标值必须能在规范化正文中找到，或是正文中两个明确数值的简单可验证计算。
- 单点数据不能输出 `trend`。
- 没有数值或表格结构时强制关闭 `chartRecommended`。
- `dataInsight` 不合法时降级为普通事实摘要，而不是显示不可靠洞察。

## 默认场景动作

### 数据结构

服务端维护受控动作目录。模型只产生场景识别与证据，不能提供按钮文案或 Agent 指令。

```ts
interface MailSceneAction {
  id: string;
  scene: string;
  label: string;
  icon: "chart" | "upload";
  agentPrompt: string;
  risk: "none" | "confirmation_required";
}
```

动作目录中的每项由以下部分构成：

- 稳定 ID 和场景名称。
- 基于邮件事实与业务状态的可用条件。
- 固定的展示信息。
- 受控的 Agent 指令模板。
- 风险等级。

邮件详情接口或智能结果接口返回已解析的 `sceneActions`。前端不重复推导识别条件。

### 首批场景

#### 监控数据：生成图表

出现条件：

- `dataInsight.kind === "monitoring_report"`。
- `dataInsight.chartRecommended === true`。
- 当前摘要版本与正文版本一致。

预填指令：

> 分析当前邮件中的监控数据，提炼核心指标、异常点和趋势，并基于可验证数据生成图表；不要推测无证据的原因。

风险等级为 `none`。点击只预填，不自动发送。

#### 发票处理：上传至发票平台

出现条件：

- 现有确定性发票识别或发票智能分类命中。
- 存在符合现有规则的可上传附件。
- 发票状态不是已上传或已关联本人。

预填指令：

> 上传当前邮件中符合条件的发票附件至发票平台。

风险等级为 `confirmation_required`。用户发送后，Agent 继续使用现有 `find_invoice_attachments`、`propose_allowance_invoice_upload`、Pending Action 和确认执行链路。默认附件选择、安全校验和上传状态记录保持不变。

### 扩展边界

新增默认场景时只需增加：

1. 一个服务端识别器或复用现有业务状态。
2. 一项受控动作定义。
3. 对应 Agent 能力与风险策略。
4. 聚焦该场景的测试。

邮件详情组件、动作组件和 Agent 打开逻辑不需要为每个场景增加专用分支。

## 前端设计

### 智能卡

现有 `EmailIntelligenceCard` 继续作为邮件正文上方的智能信息容器：

- 普通邮件标题为“摘要”，保持当前简洁展示。
- 监控数据邮件标题为“数据洞察”。
- 数据洞察先显示一句结论，再显示最多 4 个核心指标和最多 3 条发现。
- 场景动作统一显示在卡片底部。
- 没有可渲染摘要但存在场景动作时，智能卡仍可显示紧凑动作区。

通用 `EmailSceneActions` 只接收服务端返回的动作列表和点击回调，不包含业务识别规则。

### Agent 打开行为

点击场景动作时：

1. 保持当前邮件选中。
2. 调用 `openEmailAgentConversation(emailId)`，确保 Agent 绑定当前邮件。
3. 调用现有 `requestAgentComposerInput(agentPrompt)`。
4. 如果 Agent 面板关闭则打开。
5. 聚焦输入框并把光标放在预填文本末尾。
6. 不自动提交。

该流程抽成单一的 `openMailSceneAction(action, emailId)` 前端辅助函数，自动化中心等既有预填入口不受影响。

## 错误处理与降级

- 正文未就绪：不显示旧摘要或场景动作，后台等待正文补齐。
- 摘要重算失败：保留邮件正文正常阅读能力，不回退展示已知陈旧结果。
- 数据洞察校验失败：显示普通事实摘要，不显示“生成图表”。
- 场景动作解析失败：不显示动作，不影响摘要、附件和正文。
- Agent 未配置或执行失败：由现有 Agent 错误状态提示，点击入口本身不吞掉错误。
- 图表数据不足：Agent 应说明数据不足，不强制产出空图。
- 发票上传失败：继续使用现有 Pending Action 执行结果和附件状态，不在场景动作层另存状态。

## API 与类型影响

预期调整：

- `SummaryResult` 增加可选 `dataInsight`。
- AI 结果元数据增加正文版本与内容指纹。
- 邮件智能结果响应增加 `sceneActions: MailSceneAction[]`。
- 前端 WeMail 类型同步增加上述字段。

兼容原则：

- 旧版摘要没有 `dataInsight` 时按普通摘要渲染。
- 未部署场景动作的响应按空数组处理。
- 不修改现有 Agent Pending Action 协议和发票动作类型。
- 不把原始正文、附件路径或敏感命令放入 `agentPrompt`。

## 测试方案

### 服务端单元测试

- 正文未缓存时摘要任务延迟，不生成“空正文”成功结果。
- 正文补齐后旧摘要因版本或指纹变化而重置并重新生成。
- 历史无版本摘要只触发一次兼容重算。
- HTML 表格可以进入摘要上下文。
- 有正文时拒绝接受模型返回的“正文为空”。
- 单点监控快照只产生 `fact`/`anomaly`，不产生 `trend`。
- 多时间点数据允许趋势发现。
- 普通数字、日期、订单号不会启用图表动作。
- 监控表格命中“生成图表”动作。
- 发票邮件仅在存在可上传附件且状态允许时命中上传动作。
- 模型输出不能覆盖动作文案或 Agent 指令。

### 前端组件测试

- 普通摘要继续显示“摘要”。
- 监控邮件显示“数据洞察”、指标、发现和“生成图表”。
- 不可绘制数据不显示“生成图表”。
- 发票动作与图表动作由同一 `EmailSceneActions` 渲染。
- 点击动作绑定当前邮件、打开 Agent 并预填文本，但不自动提交。
- 陈旧摘要状态不渲染旧内容。

### 集成与回归测试

- 模拟元数据先到、正文后到的真实同步顺序，验证最终摘要只基于完整正文。
- 使用含 HTML 表格的监控邮件验证洞察和动作。
- 从“生成图表”进入 Agent，验证 Agent 能读取当前邮件并调用现有 Design Artifact 流程。
- 从“上传至发票平台”进入 Agent，验证仍产生确认卡且未确认前不执行上传。
- 运行服务端、渲染器类型检查和相关测试；桌面端构建后验证窗口、正文、动作和 Agent 预填交互。

## 实施拆分

1. 增加摘要正文版本/指纹元数据及陈旧结果失效逻辑。
2. 扩展摘要协议、提示、校验和监控数据测试。
3. 增加服务端默认场景动作目录与两个首批场景。
4. 增加统一前端动作组件和 Agent 预填辅助函数。
5. 补齐前后端测试并按桌面构建流程验收。

## 验收标准

- 截图所示监控邮件不再显示“正文为空”或只复述业务名称。
- 洞察内容忠实反映邮件表格中的核心指标、异常和可证实趋势。
- 仅符合条件的监控/报表邮件显示“生成图表”。
- 点击“生成图表”后，当前邮件保持打开，Agent 输入框出现可编辑的预填指令且没有自动发送。
- 符合条件的发票邮件通过同一动作组件显示“上传至发票平台”，上传仍需用户确认。
- 正文更新后旧洞察不会继续显示。
- 普通邮件摘要行为无回归。
