# 邮件图片加载与重复渲染性能设计

日期：2026-07-17
状态：待用户评审

## 背景

邮件正文已经持久化在 SQLite，并由 React Query 缓存详情数据，但 HTML 正文通过 sandbox iframe 的 `srcDoc` 渲染。线程消息收起或用户切换邮件时，iframe 会被卸载；再次打开时需要重新清洗和解析 HTML、创建 iframe 文档、加载或解码图片，并重新测量正文高度。

CID 内嵌图片当前通过本地附件接口按需读取。附件接口有 64 MB 的进程内 LRU，但缓存不跨应用重启，单项超过 10 MB 时不缓存，同一附件的并发冷请求也不会合并。浏览器响应仅缓存 5 分钟。缓存未命中时，每个 CID part 都会单独经过 IMAP 下载。

外链图片直接从 iframe 访问第三方服务器。其速度、缓存和追踪行为取决于第三方响应，WeMail 当前无法保证重复打开时的命中率，也不能隐藏用户网络地址。

## 目标

- 已经成功加载过的 CID 图片在重新打开邮件时不再访问 IMAP。
- 同一附件的并发冷请求只执行一次底层下载。
- 重新创建 iframe 时复用已处理的安全 HTML，避免重复执行完整清洗和多轮 DOM 解析。
- 线程消息收起再展开时保留现有 iframe 和图片解码结果。
- 减少图片加载期间的高度测量、`postMessage` 和 React 状态更新。
- 保持现有 sandbox、CSP、DOMPurify 和外链打开安全边界。
- 为后续外链图片代理留下明确接口，但不在第一阶段引入 SSRF 风险。

## 非目标

- 第一阶段不代理或永久保存第三方外链图片。
- 不保留所有访问过的完整 `EmailPanel` 实例。
- 不允许邮件脚本、same-origin iframe 权限或应用主题进入邮件正文。
- 不改变正文同步窗口、MIME 解析和邮件列表分页策略。
- 不以正文、图片 URL、附件文件名或邮件 ID 作为性能日志内容。

## 方案比较

### 方案 A：只保留 iframe

收起和切换邮件时隐藏旧 iframe，不卸载。

优点是实现后热打开最快。缺点是每个保留的 `EmailPanel` 都会继续占用 DOM、图片解码内存，并可能保持智能能力轮询和组件状态。跨邮件无限保活不可接受。

### 方案 B：只增加资源缓存

允许 iframe 正常销毁，但把 CID 图片和已处理 HTML 持久或内存缓存。

该方案资源边界清晰，也能跨应用重启复用 CID 图片。不过线程消息每次展开仍要重新创建 iframe、解析文档和恢复布局。

### 方案 C：资源缓存为主，局部保活为辅

采用持久 CID 缓存、请求合并和安全 HTML LRU，同时只在线程消息收起场景保留 iframe。跨邮件切换仍卸载旧详情，依靠资源缓存实现快速恢复。

这是推荐方案。它覆盖首次冷加载、重复打开和线程展开三种路径，同时避免完整详情页长期保活带来的内存与轮询问题。

## 架构设计

### 1. 附件资源缓存服务

新增独立的 `MailAttachmentCache` 服务，由应用 composition root 创建并注入邮件路由。路由不再直接持有临时 `Map`。

缓存采用两级结构：

- 一级为当前 64 MB 的进程内 LRU，用于避免磁盘读取和重复 Buffer 分配。
- 二级为 `<dataDir>/mail-attachment-cache/` 下的 512 MB 文件 LRU，用于跨邮件切换和应用重启复用。

缓存 key 由 `account-scoped emailId + attachmentId` 生成 SHA-256 文件名，不在磁盘路径中暴露邮箱地址、文件名或文件夹名称。附件 MIME 和 disposition 继续以邮件仓库中的元数据为准，不单独信任缓存文件扩展名。

写入流程必须使用同目录临时文件和原子 rename，避免进程退出后留下可被当成成功缓存的半文件。读取失败或文件长度异常时删除该项并回退到 IMAP。

邮件 part 在稳定 message id 下是不可变资源，因此成功响应使用：

- `Cache-Control: private, max-age=31536000, immutable`
- 基于缓存内容摘要的 `ETag`
- 匹配 `If-None-Match` 时返回 `304`

内存缓存继续只接收不超过 10 MB 的单项；磁盘缓存只接收不超过 50 MB 的单项。更大的附件仍可正常返回，但不进入持久缓存。磁盘项没有按时间强制过期，超过 512 MB 总预算时按最近访问时间淘汰。后续如果加入用户可配置清理策略，清理服务只操作该专用目录，不扫描其他数据目录。

### 2. 冷请求合并

`MailAttachmentCache` 内维护 `Map<cacheKey, Promise<CachedAttachment>>`。流程为：

1. 查询内存缓存。
2. 查询磁盘缓存。
3. 查询同 key 的进行中 Promise。
4. 仅第一个请求调用 `provider.fetchAttachment`。
5. 成功后原子写盘、写入内存并唤醒所有等待者。
6. 无论成功或失败都清理进行中 Promise；失败不写负缓存。

不同附件可以并行，同一附件不得重复下载。

### 3. 安全 HTML 处理缓存

把 `EmailIframe` 内的 HTML 处理提取为单一的 `prepareEmailDocument` 路径。该路径负责：

- DOMPurify 清洗。
- CID 已由调用方重写后的 URL 保留。
- 远程 HTTP 图片升级处理。
- 外链标记。
- 可选搜索词高亮。
- 拼装最终 `srcDoc`。

清洗后的 DOM 只执行一次遍历完成图片、链接和高亮修改，避免当前连续创建多个 `<template>` 的模式。DOMPurify 自身的解析和 iframe 最终解析仍然保留，这是安全隔离所必需的。

最终 `srcDoc` 使用受大小限制的模块级 LRU 缓存。key 包含正文内容摘要、搜索高亮词、auto-size 模式和渲染模板版本。缓存按总字符数限制为约 8 MB，并限制最多 20 项；模板或安全策略变化时通过版本字段自然失效。

缓存只存在于渲染进程内，不写入磁盘，因为原始 HTML 已在邮件数据库中持久化，重复保存收益有限且扩大敏感内容副本范围。

### 4. 线程收起保活

`ThreadMessage` 不再在收起状态完全移除正文渲染器。首次展开后，正文区域保持 mounted；收起时使用不可见容器隐藏，并保留 iframe 高度和已解码图片。

尚未展开过的历史线程消息不得提前创建 iframe，避免长线程一次性加载所有图片。组件需要记录 `hasBeenExpanded`：

- 初始收起且从未展开：不渲染正文。
- 首次展开：创建正文。
- 后续收起：隐藏但不卸载。

切换到另一封顶层邮件时，整个旧 `EmailPanel` 仍正常卸载，不建立跨邮件组件保活池。

### 5. 高度测量

iframe 内只保留一个合并后的高度上报调度器：

- 初始文档完成后上报一次。
- 使用 `ResizeObserver` 观察正文尺寸变化。
- 图片 `load/error` 只作为兼容性补充。
- 同一 animation frame 内的多次事件合并为一次测量。
- 高度与上次一致时不发送 `postMessage`。
- 删除全子树 `MutationObserver` 和四个固定延迟 timer；仅在 `ResizeObserver` 不可用时保留一个短延迟 fallback。

父页面收到高度后同样只在整数高度实际变化时更新 React state。

### 6. 外链图片的阶段边界

第一阶段继续直接加载外链图片，但在渲染契约中预留“阻止外链图片”设置和未来代理入口。外链代理属于独立安全子项目，必须包含：

- 仅允许 HTTP/HTTPS。
- 拒绝 loopback、私网、链路本地地址和 DNS rebinding。
- 限制重定向次数、响应体大小、内容类型和超时。
- 不转发客户端 cookie、认证头和任意请求头。
- 使用独立缓存 key 和保留策略。
- 提供按邮件或全局阻止外链图片的用户控制。

在这些约束完整设计和测试前，不把任意远程 URL 接入本地代理。

## 数据流

### CID 图片冷加载

1. HTML 中的 `cid:` 被重写为本地附件 URL。
2. iframe 请求附件接口。
3. 缓存服务依次查询内存、磁盘和进行中请求。
4. 缓存未命中时通过 IMAP 下载一次。
5. 成功结果原子写盘并进入内存 LRU。
6. 路由返回长期私有缓存头和 ETag。

### CID 图片热加载

1. Chromium 命中自身 HTTP 缓存，或向本地接口进行条件请求。
2. 本地接口从内存或磁盘返回，不访问 IMAP。
3. iframe 只承担图片解码和绘制。

### 正文重新打开

1. React Query/SQLite 提供邮件正文。
2. `srcDoc` LRU 按内容摘要命中已处理文档。
3. 新 iframe 解析已处理 HTML。
4. CID 图片命中浏览器、本地内存或磁盘缓存。

## 错误处理

- 磁盘缓存目录无法创建时降级为进程内缓存，不影响邮件阅读。
- 磁盘缓存读取或摘要校验失败时删除损坏项并重新获取。
- IMAP 下载失败时所有等待请求收到同一失败结果，但后续请求仍可重试。
- 原子写盘失败时仍返回本次已下载字节，只是不获得跨重启缓存。
- HTML 处理失败时不得回退到未清洗 HTML；显示纯文本正文或安全错误状态。
- iframe 高度消息异常时保持合理最小高度和外层滚动能力。
- 性能日志只记录阶段、耗时、字节数、缓存层和错误类别。

## 测试设计

### 服务端

- 内存命中不调用 provider。
- 磁盘命中不调用 provider，并在应用重建缓存服务后仍可读取。
- 两个并发同 key 请求只调用一次 provider。
- 不同 key 可以独立完成。
- 下载失败不会留下缓存文件或永久进行中状态。
- 超过内存单项上限但不超过磁盘单项上限的文件仍可写入磁盘并从磁盘复用。
- 磁盘缓存超过总预算时淘汰最久未访问的项目。
- 超过磁盘单项上限的附件正常返回但不持久化。
- 临时文件不会被当作有效缓存。
- ETag 匹配返回 `304`，成功响应包含长期私有 immutable 缓存头。
- 缓存路径不包含原始邮件 ID 或附件名。

### 前端

- 同一正文重新挂载时命中 prepared-document LRU，不重复执行清洗。
- 正文、搜索词或模板版本变化时缓存失效。
- LRU 同时受项目数和字符预算约束。
- HTML 图片、链接和高亮在一次变换结果中保持正确。
- 历史线程消息首次展开前不创建 iframe。
- 展开后收起再展开复用同一个 iframe DOM 节点。
- 高度相同的重复消息不触发 React state 更新。
- sandbox、CSP、主题隔离和外链拦截测试继续通过。

### 手动验收

- 选择一封包含多张 CID 图片的邮件，首次打开后切换到其他邮件再返回，确认不再产生 IMAP attachment fetch。
- 重启桌面应用并重新打开同一邮件，确认图片来自磁盘缓存。
- 在线程中展开、收起、再展开同一消息，确认图片不闪白且 iframe 节点未重建。
- 使用包含大量 table、链接和图片的营销邮件检查正文首屏和滚动稳定性。
- 断网后重新打开已经缓存的 CID 图片邮件，确认图片仍可显示；未缓存外链图片允许失败。

## 可观测性与成功标准

增加不包含邮件内容的性能事件：

- `mail.attachment.cache.hit`：`memory | disk`
- `mail.attachment.cache.miss`
- `mail.attachment.fetch.duration_ms`
- `mail.attachment.fetch.bytes`
- `mail.body.prepare.duration_ms`
- `mail.iframe.first_height.duration_ms`

成功标准：

- CID 图片热打开和应用重启后的再次打开均为零次 IMAP 下载。
- 同一 CID part 的并发请求 provider 调用次数严格为 1。
- 线程收起再展开不创建新的 iframe。
- 常规邮件的 prepared-document 热命中不重新执行 DOMPurify。
- 图片逐张加载时，每个 animation frame 最多上报一次高度，且相同高度不更新 React state。
- 不降低现有 XSS、sandbox、CSP、隐私日志和外链导航测试覆盖。

## 推进顺序

1. 实现 `MailAttachmentCache`、磁盘缓存、请求合并和 HTTP 缓存契约。
2. 提取 `prepareEmailDocument` 并加入受限 LRU。
3. 调整线程收起生命周期。
4. 简化 iframe 高度上报。
5. 加入性能事件和桌面手动验收。
6. 将外链图片代理作为后续独立设计，不与本次性能修复绑定发布。
