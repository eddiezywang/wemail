# 确认操作与持久执行任务重设计

状态：发票上传链路已实施，并完成一张真实发票的手动确认、平台入库、重启恢复和后续只读查询验收；其他未执行的验收项仍不视为通过。

## 问题与代码证据

1. `AgentPanel.handleResolvePendingAction` 点击即设置 resolving，`PendingActionCard` 将其显示为“正在上传”；这只是请求状态，不是执行进度。
2. `api.request` 默认 30 秒超时，普通确认没有专用期限；`AllowanceInvoiceService.uploadFromMailAttachments` 串行下载并执行多个各自有 30 秒期限的 WeCLI 命令。HTTP 请求生命周期不适合作为批任务生命周期。
3. 确认卡用 void 丢弃处理结果；普通网络超时没有 execution 载荷，catch 返回的 error 没有可见展示。安装流程有专门反馈，但普通操作缺失。
4. resolve 路由先 reserveExecution，随后等待完整执行和可选 Agent continuation，最后返回。预留后的学习记录、确认轨迹在执行 try/catch 外；这些辅助步骤抛错也可能让记录停在 executing，实际执行器尚未调用。
5. 附件结果先放在内存数组，全部完成后才由 MailActionExecutor 更新发票状态。进程中途退出会丢失已完成条目的本地执行证据。
6. 整体只记录 executing/succeeded/failed/outcome_unknown，无法表达三个附件的部分成功；不同 actionId 的新清单不受旧 actionId 的幂等保护。
7. WeCLI 超时只说明本地等待结束，平台可能已经受理。当前失败结果没有清晰区分“确定未提交”和“提交结果未知”。杀死本地子进程不能撤销远端操作。

## 用户可见行为

- 确认后先显示“已确认，等待执行”，收到任务开始状态后才显示具体阶段。
- 同一卡片展示每个附件：等待、下载中、提交中、核对中、成功、确定失败、结果待核实。
- 关闭侧栏、刷新或请求断开不会删除或重复创建任务。重新打开从任务快照恢复。
- 请求超时显示“提交结果暂未确认，正在查询任务状态”，按 actionId 查询，不能显示上传失败或自动生成新清单。
- 已成功的附件不重复上传；只对确定失败、且授权仍适用的条目提供明确的重试入口。
- 未知结果优先只读核对平台。缺少可靠核对能力时保持“结果待核实”，交给用户检查，不能将未知转换成可自动重试。
- 停止操作只停止后续未提交条目，当前远端提交可能仍生效；不宣称回滚。

## 职责与数据

保留 `agent_pending_actions` 作为不可变授权记录；新增领域执行记录及逐项记录，不把整个动作包装成一个会自动重放的 AI job。

| 记录 | 责任与关键字段 |
| --- | --- |
| pending action | 账号/所有者、动作类型、权威参数快照及 hash、授权期限、确认/拒绝时间、唯一幂等键 |
| action execution | executionId、唯一 actionId、账号、排队/运行/终态、revision、执行租约与 generation、开始/更新时间、聚合结果 |
| execution item | executionId + itemId、来源附件及目标平台账号、准备后内容 hash、阶段、尝试号、提交前标记、平台回执、审计关联、结构化错误 |

执行状态：queued → running → succeeded / partially_succeeded / failed / outcome_unknown / cancelled。
逐项区分阶段与结果；混合未知项时聚合保留未知，不仅以成功/失败计数判定终态。已知成功项不回退。

执行器使用授权记录中的权威参数，不重新采用模型或客户端提供的命令；从真实邮件/附件元数据校验账号、附件存在性、类型、大小和所选清单。文件 hash 由可信下载结果计算，不接受模型提供的 hash 作为身份。
执行计划版本及业务目标固定，避免配置改变后以旧确认执行新行为。不能将隐藏的新参数排除在授权范围外。

## 确认协议与事务

1. POST 现有 resolve 路由完成账号归属、参数 hash、幂等键、期限校验。
2. 在数据库 writer 的一个短事务内，确认授权并创建唯一执行记录、逐项清单、排队状态；授权与执行记录不能分别提交。
3. 提交后返回 202，包含 actionId、executionId、当前状态和 revision。重复确认返回同一 executionId 和现有状态；已过期/参数不一致明确拒绝，不重建任务。
4. 事务提交后通知 dispatcher。通知丢失时，启动恢复及有限到期唤醒可发现持久 queued 记录；不依赖内存中的 Promise 或 setInterval 全表扫描。
5. 增加按 executionId 查询快照、按 actionId 查执行记录的账号隔离接口；结果未读到不能被当成“允许重做”。
6. 用户行为记录、会话轨迹和后续 Agent 总结不阻塞授权提交或任务执行。后续总结以 executionId + 结果版本幂等入队，失败不能改变业务执行结果。

授权在接受时检查过期；已经接受的任务不能因确认卡原始 expiresAt 到点而中途变成“未授权/已过期”。撤销尚未接受的授权和停止已接受任务是两个操作。

## 后台执行与恢复

- 复用数据库 writer RPC、短事务、租约和到期唤醒的已有模式；新增 action execution 领域方法。状态表是执行队列事实来源，避免再维护第二份容易漂移的 job 状态。
- 独立受限执行 worker 承担 WeCLI/进程处理，不占用 AI worker pool，不让同步进程清理或 SQLite 锁等待阻塞 Electron 主线程；附件读取通过现有 Mail Core 能力完成。
- 起步同一平台账号串行执行；只在事件到达或最早租约到期时唤醒。并发限制不是全库扫描的理由。
- 下载/准备结果和逐项进度及时落盘；开始任何远端写操作前先提交“即将提交”标记，提交后立即持久化回执及发票投影，再处理下一项。命令输出不等于业务成功，适配器按平台返回结构解析上传/OCR/确认结果。
- 更新必须带租约 generation 校验，旧 worker 的迟到结果不能覆盖当前权威状态。租约过期只允许接管核对流程，不能直接重新发送可能已提交的命令。
- 下载等无副作用阶段可有限重试；进入提交边界后超时、断连、退出一律先标未知并核对。平台明确拒绝才是确定失败。
- 本地 action 幂等不能保证远端 exactly-once。优先使用平台原生幂等键；没有时，以目标平台账号、可信文件 hash/发票身份及提交记录做重复检测和核对，不能仅凭文件名判定。
- 同一内容的新 actionId 也要检查已有活动/成功/未知记录，明确提示重复或待核对；仍需支持用户在明确业务需要时发起新的授权，不能永久禁止同内容操作。

## 状态同步与界面

数据库提交后的事件携带 executionId + revision；前端先订阅再读取快照，按 revision 合并，避免快照与事件竞态、重复和乱序。连接恢复必须重新读取快照，事件不是唯一事实来源。
复用现有本地 API/SSE 与 Electron 桥接模式；只订阅当前账号相关执行状态，断线期间对可见活动任务有限退避查询，不做新的全局高频轮询。
移除以 resolving 推断“上传中”的逻辑；resolving 仅显示“正在提交确认”。完成、部分成功、失败、未知均在原卡片保留可见结果。
错误返回结构化 code/阶段/条目，不在卡片泄露本地文件路径、凭据或原始命令输出。

## 改动范围与兼容

- shared：授权响应、执行快照、逐项状态与事件协议。
- DB schema/writer/reader：执行记录、索引、原子确认入队、租约、逐项提交和状态查询；继续遵守单 writer。
- agentRoutes：移除请求内长时间执行，保留精确授权、账号归属与幂等校验。
- AgentActionExecutor/MailActionExecutor/AllowanceInvoiceService：增加领域执行上下文和逐项落盘，拆开准备、远端提交与核对，消除先积累整批结果再保存。
- WecliSkillRuntime/审计：取消、期限、进程生命周期和结构化结果；提交未知不自动重放，后台通过 writer 异步审计。
- AgentPanel/pendingActions/PendingActionCard：独立确认请求状态与业务执行状态，统一可见错误，恢复快照和结果。
- bootstrap/Electron：执行 worker 生命周期、事件发布、启动恢复。
- Agent continuation/发票状态：业务结果提交后投影及幂等通知，不参与业务事务之外的成功判定。

旧 pending 可继续请求授权；旧 succeeded/failed 原样展示。旧 executing 不自动重跑，转换为“结果待核实”并优先检查旧审计。切换时不能让旧请求执行器和新 worker 同时处理同一动作。
MCP 当前“确认只授权，外部客户端另行提交”的契约保持原语义，不能因改造桌面确认链路而隐式执行 MCP 操作。通用接口按动作能力接入，先完成发票上传纵向闭环，再迁移其他桌面确认动作；旧动作兼容期间明确标记支持范围。

## 实施顺序与验收

1. 定义状态与契约、执行表和原子确认入队，完成账号/参数/重复确认约束。
2. 实现后台调度和逐项上传/核对，接入 writer，验证提交边界崩溃恢复。
3. 卡片改用任务快照及事件，移除无反馈超时和推测进度；接通最终会话总结。
4. 迁移旧记录和其他桌面确认入口，关闭旧长请求执行路径。

必要验收：双击/重复请求/确认响应丢失只建一个任务；确认事务任一步失败不能留下半授权；三个附件运行超过 30 秒仍有真实进度；第二项失败保留第一项成功；提交前/提交后/回执落盘前退出分别恢复；旧 worker 迟到不能覆盖；关闭侧栏/刷新/重启恢复；事件重复乱序/断线重连正确；跨账号拒绝；参数变更拒绝；新清单不能绕过成功/未知项去重；停止不虚报远端撤销；结果总结失败不改变上传结果。

验收按实际平台回执及逐项记录核对，HTTP 202、进程存活或卡片动画均不算上传成功。
