"没有 payload" 是 pending 还是 skipped？

app/components/wemail/IntelligenceStatus.{tsx,test.tsx}
新设计区分"等待异步加载"和"没东西可处理"两种空状态。loading=true 时显示"等待中"；loading=false（默认）就是"已跳过"。测试夹具 payload={null} 不带 loading，所以组件返回 skipped，但测试还在期望 pending。

  const pill = screen.getByTestId("wemail-status-summary");

组件实际行为

IntelligenceStatus.tsx · line 49-51
function deriveStatus(payload, loading, error, kind) {
  if (error)    return "failed";
  if (!payload) return loading ? "pending" : "skipped";
  ...
}
// payload=null + loading 默认 false → "skipped"
判定 组件是新规范，测试是旧期望。有一条相邻的测试 "shows pending when loading is true" 显式传了 loading 还是过的，证明语义是有意分裂的。修法：把这一条断言改成 "skipped"。

失败状态的内容容器谁来渲染？

app/components/wemail/EmailSummaryCard.{tsx,test.tsx} + AICard.tsx
UI 改造把"failed 状态显示什么"从子组件提到了通用 AICard 容器里。AICard 看到 state="failed" 就自己渲染 <p data-testid="ai-card-failed">，并且 showBody=false → children 不渲染。所以 EmailSummaryCard 内部的 <div data-testid="wemail-summary-content"> 永远不会出现在 DOM 里。

组件实际行为

AICard.tsx · line 77, 102-113
const showBody = state !== "failed";
return <section data-state={state}>
  <header>...</header>
  {state === "failed" ? <p data-testid="ai-card-failed">...</p> : null}
  {showBody && children ? <div data-testid="ai-card-body">{children}</div> : null}

判定 组件做了正确的关注点分离，测试在用旧的 DOM 假设。AICard 集中处理 failed copy 是 stone-floating UI 的设计要点（统一观感、避免每张卡片自己写"失败提示"）。修法：把 getByTestId("wemail-summary-content") 改成 getByTestId("ai-card-failed")，断言"AICard 渲染了失败提示"。

什么算"inline 附件"？

app/components/EmailAttachmentList.{tsx,test.tsx} + lib/utils.ts
旧约定靠 contentId 字段（HTML 邮件正文里的 cid:logo-inline）认 inline；新约定改用 IMAP 标准的 disposition 字段（"inline" / "attachment"）。过滤函数已经只看 disposition，但测试夹具还在靠 contentId: "logo-inline" 表示 inline，没设 disposition → 过滤函数读到 undefined !== "inline" → true → 这个附件被当作普通附件渲染出来。

测试夹具 + 期望

EmailAttachmentList.test.tsx · line 27-33, 61-70
const inlineImageAttachment: Attachment = {
  id: "att-3",
  filename: "logo.png",
  mimetype: "image/png",
  size: 1024,
  contentId: "logo-inline",  // 旧 inline 标记
  // disposition 字段缺失
};

it("filters out inline attachments", () => {
  render(<EmailAttachmentList attachments={[inlineImageAttachment]} />);
  expect(screen.queryByText("logo.png")).toBeNull();
});

组件实际过滤逻辑

app/lib/utils.ts · line 234-236
export function getNonInlineAttachments(attachments?: Attachment[]) {
  return attachments?.filter(
    (a) => a.disposition !== "inline"
  ) ?? [];
}

// 测试夹具的 disposition === undefined
// → undefined !== "inline" === true
// → 附件被保留 → "logo.png" 渲染出来 → 测试 fail
判定 过滤逻辑选了一个简单可靠的字段做单一信号，测试夹具忘了同步。修法两选一：
(a) 给 inlineImageAttachment 加 disposition: "inline"（保留语义）
(b) 把 getNonInlineAttachments 改成 contentId 非空 || disposition === "inline" 都算 inline（兼容旧数据）
选 (a) 更简单 — 这是测试夹具陈旧；如果生产数据里有 contentId-inline 但没 disposition 的真实邮件，再选 (b)。

A. 更新 3 个测试，让 8 个失败全过

对每一处差异选刚才"判定"段写的修法（差异 1: 改断言；差异 2: 换 testid；差异 3: 给夹具加 disposition）。每处改 1-3 行测试代码，零组件改动。

选它如果：你认同三处都是"测试旧、组件新"的判定（我已逐项给出依据）。耗时约 10 分钟，附带在 merge commit 后多加一个独立 commit。

B. 在本 PR 里跳过这 8 条测试 + 留 issue 链接

给 3 个 describe 或 it 标 .skip 加一行注释 // TODO(#NNN): align with stone-floating UI overhaul。技术债显式，reviewer 一般会接受。

选它如果：怀疑判定可能错（比如担心是组件该改回去），不想代笔下结论；或不想让本 PR 跨 UI 主题。

C. 不动测试，单独提 issue / PR 让 UI owner 判
