# 未点击邮件无法读取正文的排查

已知机制：首次登录后，WeMail 会先分批同步主题、发件人、状态等元数据。对正文尚未缓存的邮件，系统会创建后台正文补全任务；历史邮件按新近程度优先拉取并保存正文。系统还会定期检查正文缺失或补全失败的邮件，重新安排可重试任务。

用户在 WeMail 中点开某封邮件时，该邮件的正文获取会进入前台交互通道。因此，“智能助手按范围查询时部分邮件没有正文，人工点开后就能读取”至少说明：查询时本地正文仍缺失，而随后对这封邮件的交互式获取成功。它支持“后台正文补全尚未成功”的判断，但仅凭用户现象不能继续断言任务未入队、队列积压或重试失效。点击是临时补救，不是正常使用智能助手的前置条件。

这个现象不能仅用“同步慢”解释。如果首次同步后已等待较长时间，同一查询范围内仍有部分邮件正文为空，应按“首次同步的后台正文补全遗漏、失败或未完成”记录案例。现有证据不足以进一步确认是任务未入队、后台队列积压、拉取失败还是重试未生效，需要结合同步和任务状态定位。

客服应根据用户当次截图描述实际可见的系统名、数量和状态，不把历史案例中的名称或数字当作通用事实。通用判断是：同一批邮件中部分已有正文、部分正文为空，而人工打开后立即恢复，说明元数据已经同步，但后台正文补全没有完整完成；人工点击只是前台优先获取，不是智能助手正常工作的前置条件。

## 最短验证与临时处理

1. 记录首次登录/同步开始时间，以及智能助手查询的明确时间范围；
2. 选一封正文缺失的邮件，先不要打开，记录智能助手返回的缺失现象；
3. 在 WeMail 中打开同一封邮件，待正文显示后对同一范围重试智能助手。若只有点开后恢复，即形成“后台缺失、前台成功”的最短证据链。

如果用户只需立即读取少量已知邮件，可临时先在 WeMail 中打开目标邮件，待正文显示后再重试智能助手。对范围查询或批量邮件，这不是可接受的解决方案，不能代替建单和修复。也不要要求用户逐封点击来完成首次同步。

## 进入诊断取证

如果同一范围等待约一小时后仍有多封邮件正文为空，并且同一封邮件人工点开后立即恢复，最短现象证据已经成立。此时不要继续追问版本，也不要停在“任务遗漏、队列积压、拉取失败或重试未生效都有可能”；下一步应取得诊断包来区分这些方向：

1. 打开“设置 → 高级设置 → 诊断”，开启“调试日志”；
2. 保持一封正文缺失的邮件未打开，用智能助手对同一范围再查询一次，复现后立即回到诊断页关闭调试日志；
3. 点击“导出诊断包”。诊断包虽经脱敏，仍可能包含用户名、本机路径、账户标识、时间和运行环境等个人或企业信息，因此优先建议私聊发送；但用户选择直接发到群聊时，助手也应正常接收和分析，不能拦截或要求重复上传。

如果排查从群聊发起，只有助手确认下一步必须转私聊传递诊断材料时，才把上述最小现象建立为一个交接案例，在群里回复一次真实 `case_id`，再请同一用户私聊发送“继续排查 {case_id}”和诊断 ZIP。普通问答、尚未进入传包阶段的排查、同一问题的图片或文字补充都不创建新编号。私聊侧按企微 User ID 校验案例归属，只恢复该用户案件中的脱敏现象摘要，不合并整个群聊记录。用户没有附案例编号时，只能在恰好存在一个未结案例时恢复；存在多个则要求用户提供编号。

私聊收到诊断包时，助手应先续接同一用户的交接案例，再实际读取。用户直接把包发到群聊时则直接分析，不强制创建交接编号或要求转发一遍；群聊答复仅说明最小诊断结论，不引用可能涉及个人信息的日志原文。只有诊断证据支持时才能把问题进一步归为任务遗漏、队列积压、拉取失败或重试未生效。机器人只保留二次脱敏后的诊断摘要，收到的临时文件在分析后删除；案例中不得粘贴完整诊断包或邮件内容。

应建立 WM-03 内部案例，写明预期、实际、查询范围、正文缺失数量、等待时长、点击前后现象和诊断摘要。用户未说明版本时按最新正式版处理。内部建单成功后可以说“已记录”，普通回复不展示编号；只有确实需要转私聊传包时才展示一个 `case_id`，同一问题后续不得再次建单。失败时明确“暂未记录成功”。

不要收集邮件正文、附件或完整通信对象；必要截图遮盖主题、姓名和邮箱，仅保留时间、数量、状态和脱敏消息标识。凭据失效与永久性超大邮件等错误需要依据诊断状态另行分流，不能都归为“同步慢”。
