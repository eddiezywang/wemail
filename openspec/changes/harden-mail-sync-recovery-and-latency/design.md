## Context

当前调用链为 Electron Main supervisor → Mail Core → MailCoreAccountRuntime → Account Worker → ImapSmtpMailProvider → DB Service Writer。列表通过本地数据库读取和提交事件更新。独立 provider 已存在，但实时元数据与正文仍共用账户后台调度槽，物理连接隔离没有消除调度阻塞。

本次处理单账户常驻桌面运行、长时间离线补拉、大量文件夹及正文积压场景。方案不承诺网络故障时零延迟；要求无静默停收、无游标跳跃遗漏，并可区分本地排队和远端耗时。

## Goals / Non-Goals

目标：线程或网络恢复后无需重启客户端；单次任务耗尽不结束收信；检查点不跳过未提交数据；同步占用内存、连接及调度等待有界；新邮件不等待整批正文和其他文件夹完成。

非目标：同步系统重写、调整 SMTP、全量下载正文、引入新依赖或常驻连接、重新实现 IMAP、保证邮箱服务端可用性、一次性全库重扫、恢复服务端已永久删除的邮件。

## Decisions

### 1. 账户生命周期拥有恢复调度

复用 MailCoreAccountRuntime 保存账户级恢复状态。每次 Worker ready 都执行统一恢复入口，读取最新数据库游标，安排补拉；不再仅依赖首次 `start()` 的 bootstrap。需要按 Worker generation 校验 ready、结果、ACK 和退出处理，旧线程结果不能改变新线程的游标或调度状态。

区分线程存活与收信健康。临时失败保留一个账户恢复定时器，采用现有退避策略并加入抖动，正常临时故障的最大退避为 60 秒；服务端限流遵守 Retry-After。重连失败后仍可创建下一轮有限尝试，单个 durable job 的终止不取消账户恢复。认证失败暂停自动登录，凭据 generation 更新后重新进入恢复。stop、注销和账户替换清理定时器并取消等待。

手动刷新在无服务端限流时提前触发一次恢复；不绕过认证失败，不形成并发登录风暴。无 Worker、未 ready 或凭据失效时，反馈对应状态，不能只因为入队成功就表示刷新完成。

### 2. 推送与补偿检查共存，触发不丢失

每个活动账户保留一个 60 秒补偿检查定时器，即使服务器支持 IDLE 也运行。它向既有调度入口提交远端检查意图；不执行周期 claim 查询。启动、IDLE、补偿检查、手动刷新、重连和恢复共用单一元数据协调入口。

元数据运行期间合并重复触发，同时设置 pending-reconcile；当前有界页结束后再检查一次，不能把运行期间的手动或 IDLE 意图直接当作已覆盖。挂起/休眠恢复时合并过期定时器，只产生一次检查，不补发全部错过的 tick。

监听器在可用实时连接建立后及时恢复；完成一次补拉后再次检查 pending。健康判断和兜底检查独立于 `exists` 是否到达。停止后的计时回调及过期 generation 均无副作用。

### 3. UID 升序、有界页与原子检查点

文件夹标识、UIDVALIDITY 和 UID 构成进度边界。每轮捕获可处理的上界，按 UID 升序取最多 50 封一页；新到邮件由后续检查接续。不能先取最新 5,000 封再把最大 UID 当作全部已完成。UID 可以合法不连续，连续完成是指搜索返回的待处理集合已逐页确认，而不是要求 UID 数值连续。

分页同时约束远端 UID 搜索范围和本地结果数量，禁止先加载整个增量 UID 集合再切片。优先使用有界 UID 数值区间搜索并在区间内分页；稀疏区间可通过已确认的扫描位置推进。每页释放 provider 所有权，不跨页保留未经校验的 selected-mailbox 状态。

每页消息 upsert 与检查点更新在现有 Writer 同一事务内完成，提交成功才 ACK。提交前失败不前移；提交后 ACK 丢失允许重放并去重。按 UID 排序，不按 receivedAt 排序决定提交顺序。部分 FETCH 缺项须确认是已删除还是请求失败；无法确认时不能越过缺项推进检查点。

每页结果携带预期文件夹 UIDVALIDITY、扫描边界和 generation。Writer 拒绝旧世代检查点，避免旧页覆盖重建进度。初始最近窗口的实时游标与历史覆盖完成状态独立，存在 INBOX 游标不等于历史补扫已完成。

### 4. 每个文件夹独立进度

读取现有 `mail_folder_sync_state`，取消使用 INBOX internalDate 扫其他文件夹。实时 INBOX 页完成即提交并触发本地列表更新；其他文件夹按有界页公平推进，INBOX 有新触发时在下一页边界让出，避免永久饿死任一文件夹。

UIDVALIDITY 变化仅重建对应文件夹的游标。先恢复实时最近窗口，同时保留独立、可持久化的重建进度；完成配置范围内的扫描前不能宣称历史覆盖完成。重建不清空本地邮件，沿用现有身份合并规则，避免重复消息和重复自动化。

### 5. 核心元数据优先，资源与时限有界

优先复用现有实时连接和调度状态调整顺序：已到期的实时/手动元数据 → 新邮件正文 → 历史页与正文预取。正常正文不强制中断，但其后不再连续领取正文阻挡元数据。保持前台正文的现有交互能力，不把用户打开邮件的队列并入历史队列。

实时小页采用现有同步工作负载准入，后台暂停只暂停历史和预取；临界内存下通过缩小单页/单次工作量及有界等待处理，不能无期限等待后台恢复阈值。保持单 Writer 背压，不无限并发或缓存结果。

明确 IMAP 连接、单命令和 Writer 请求超时；不能仅用 Promise.race 超时后释放槽，仍让底层旧请求继续操作同一连接。超时先使旧 operation/generation 失效，再关闭或取消对应 session；若无法局部回收，终止并恢复账户 Worker。发送邮件沿用独立幂等/结果确认语义，不能因收信超时盲目重发。

拟定验收默认值：单个阻塞 IMAP 操作 30 秒上限，活动同步无远端完成或持久化进度 60 秒进入恢复。真实邮箱验收确认这些值是否适配大邮箱，修改时同步更新规格与测试，禁止用放宽时限隐藏卡死。

### 6. 健康和延迟以真实完成为依据

复用现有运行时健康契约，至少记录：最近成功远端检查、最近提交、活动阶段/开始时间/最近进度、下次检查与重试时间、连续失败、最后错误分类、Worker generation 和恢复次数。空邮箱检查成功也更新健康；空闲期间没有新邮件不等于卡死。

按 trace/run 关联记录触发→领取、远端请求、Writer 提交、事件送达和列表可见的时间；不记录正文、附件或凭据。以进度与预期下一检查判断持续停收，心跳只是线程存活信号。

刷新控件沿用局部状态，明确 accepted/shared、完成与失败。自动恢复不新增全局进度条或完成提示。历史修复保持现有通知/自动化抑制策略；重复补拉不能重复触发业务副作用。

## Migration and Existing Gaps

优先复用现有表，确有字段缺口才添加兼容迁移。旧版最大 UID 不能证明此前数据完整：在已有配置历史范围内安排一次可恢复、低优先级的逐文件夹覆盖核对（沿用初始历史配置，当前默认 180 天），持久化该修复版本及覆盖检查点。它可发现旧版截断遗漏，且不得回退实时高水位或与实时检查争抢优先级。

范围外缺口只能通过显式扩大修复范围恢复，诊断必须说明覆盖日期，不能声称全部历史已修复。中断后从检查点续跑，不能每次启动重复全范围扫描。回滚保留邮件与新增检查点，不做删库、清游标或重装数据操作。

## Delivery and Validation

分三批交付：A 生命周期、持续恢复及触发合并；B UID 页事务、各文件夹进度及旧缺口修复；C 调度、资源、健康及真实延迟。每批补充回归用例，但只有用户明确授权验证时才运行。

详见 `tasks.md` 和 `acceptance.md`。最终接受必须有真实交互和逐封收信证据；启动成功、HTTP 200、心跳正常和刷新入队不构成验收通过。

## Implementation ownership

- `electron/mail-core/entry.ts` 持有凭据、DB producer 及账户 runtime。配置重试绑定凭据和 producer 的对象身份；重载使用 generation，先串行等待旧 runtime stop，再配置新账户并读取游标，异步返回后再次核对身份。关闭时使待执行重载失效。DB 断开同样停止旧 runtime，不能沿用已关闭 producer。
- `MailCoreAccountRuntime` 持有补偿、重试、Worker 重启和进度监视 timer。每次 ready 重新建立 bootstrap；dispatch 读取已提交状态；单实时任务加单 pending 合并意图。手动刷新 RPC 和自动监听均进入 `enqueueMetadataSync`，原有 API/MCP 刷新继续复用该 Mail Core 入口。
- Account Worker 持有 realtime/history iterator、ACK 等待和 IDLE abort controller；不再负责补偿轮询。每次页命令传入最新文件夹状态，ACK 前不请求下一页；有 pending 时下一页优先 INBOX，随后让出给其他目录。
- Provider 持有真实 socket 和选中文件夹状态；页释放锁并恢复 INBOX。命令进度与页提交进度分别更新看门狗，超时关闭真实客户端。
- Writer 在现有事务内核对 metadata lease 和预期检查点，并提交消息、页游标和新增邮件的正文任务。Reader/producer 的 `mail.getSyncStates` 读取同一权威状态，查询失败不使用猜测的高水位继续提交。
- 后台正文与历史元数据按有界操作交替，实时元数据在二者之前领取。停止或替换 Worker 后晚到的领取结果立即归还租约；进度回收开始即禁止旧元数据请求继续确认完成。
- 进度超时且 SMTP 正在发送时，使用账户 Worker 的元数据取消命令，关闭实时 IMAP 并中断当前网络/ACK 等待；Worker 关闭旧 iterator 后确认取消，主进程再释放旧租约并恢复领取。发送连接与发送任务保持原有结果确认流程，旧 Writer 回调同时校验 Worker 和具体租约对象，不能在同一 Worker 恢复 ready 后确认旧页。
- Renderer 刷新使用 runtimeId/receiptVersion 等待对应完成或失败，超过观察窗口保留 queued 状态。DB 元数据插入驱动列表及计数；有界诊断通过 commitVersion 关联送达与实际视口渲染，正文和历史完成不作为可见前提。
- MCP 同步状态复用相同 runtimeId/receiptVersion，通过主进程心跳读取账户健康快照；请求前缓存不能判定本次完成，账户重载、凭据更新和进程断开清除快照。旧版无版本响应保留原任务状态兼容。
